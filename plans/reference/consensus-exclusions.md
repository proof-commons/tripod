# Consensus Exclusions · `ref:exclusions:consensus`

This register records every consensus feature this workspace has ELECTED not to support, and binds each election to the code that enforces it.

An exclusion here is a choice, not an absence. The target admits the feature; this workspace declines it, and the decline is a claim about what an owner's signature means, what a byte string is allowed to be, or what a construction is allowed to produce. A claim of that kind drifts silently unless the document that states it and the row that refuses it are tied together, which is what this register is for.

## Discipline · `rule:exclusions:discipline`

An elected exclusion mints its tag here, and the code row that enforces the exclusion cites that tag.

An exclusion's section carries its revision surface: what a future revision of this exclusion, or of any other, would have to touch.

The citation is the mechanism and this register is only its index. A citation fails when its mint is removed, so deleting a section here produces one diagnostic per enforcing row, and that list is the worklist for undoing the election. The revision surface is the wider answer the diagnostics cannot give: the doc paragraphs that argue the exclusion, the tests that reach the refusing rows, and the residuals, standings and vocabulary members whose wording rests on the exclusion holding. None of those fails when a label is deleted, and every one of them is wrong the moment an exclusion is revised without it.

The revision surfaces are written per section rather than once, because the surfaces differ: some exclusions are one refusal reached by one test, and others are a profile decision carried in four separate vocabularies across four packages.

## Single-output sighash commitments · `rule:exclusions:single-output`

**Excluded.** The owner sighash profile does not admit a commitment to the single output at the signing input's own position. The profile requires the whole-outputs dimension and refuses the single-output one, so no candidate this workspace builds is authorized over a message that leaves the rest of the transfer free.

**Ground.** The refusal is checked against the branch it refuses rather than asserted: under the single-output branch, terms 11 and 12 of the message are not written at all and are replaced by the hash of one output and the hash of one output witness at the signing input's own position, leaving every other output and every other output witness uncommitted (`tab:sighash-review:refusals`). That is what the profile's own argument says the refusal removes, so the recorded ground is the branch's actual behaviour and not a paraphrase of it. Under this profile an owner authorizes a whole transfer, a destination multiset together with an aggregate conservation, and a single-output commitment would authorize one entry of it while the rest became whatever the builder pleased. The election is the owner's, recorded at the profile decision (`rule:guide-sighash:profile-decision`), which closed the narrower hash types as profile directions for this work. A second ground stands beside the first: the refused branch also contains a bounds check that covers the output list and an index that reads the output-witness vector, two containers that are not the same object (`rem:sighash-review:single-output-index`), carried upstream as a friction (`obs:upstream:taproot-single-output-witness-index`). This arc never reaches that read, because it refuses the dimension for the first reason.

**Enforced at.** `packages/tapscript/src/authorization.rs`, the `DimensionRefusal::LeavesOtherOutputsFree` row, which is the profile's typed reason for the refusal; and `packages/target-elements/src/authorization.rs`, the `UnreviewedGround::TheSelectedProfileRefusesIt` row, which is why the dimension stays outside the reviewed set rather than counting as a gap.

**Revising this exclusion touches:** this section; the refusals table and the second-ground remark in the owner sighash review; the profile-decision ruling and its hash-type table in the owner sighash concept; the refusal row `LeavesOtherOutputsFree` and the role assignment in `selected_owner_profile` that binds it to the dimension; the unreviewed-ground row in the target's authorization module and the four-entry unestablished table that assigns it; the two profile invariants that check every offered dimension is classified and that coverage lands only on required dimensions; the tests `the_three_unreviewed_grounds_are_the_three_different_reasons` in the target's capability tests and the profile tests that assert the refused set; the upstream friction label for the unmeasured vector index, whose adaptation-site column names the review; and the recomputed disposition, because moving a dimension out of the refused set changes the required set the assessment reads.

## Input extension, the open input set · `rule:exclusions:input-extension`

**Excluded.** The profile does not admit an input type that commits only to the signing input and permits further inputs to be added after signing. The whole-inputs dimension is required and the extension-permitting one is refused.

**Ground.** Under the extension-permitting branch seven message terms are not written at all and are replaced by the signing input's own outpoint flag, outpoint, spent asset, spent value, spent script, sequence and issuance (`tab:sighash-review:refusals`). An added input is an added source of the conserved asset, so a transfer the owner signed as balanced becomes one that moves value the owner never saw. The recorded ground understates the effect and the review says so: what the branch opens is not only the input set but the whole spent-output census for every input but one, which is what makes the spent-outputs dimension a whole-transaction dimension at all. A profile admitting the extension would be claiming a census-wide commitment the message does not make. The election is the same ruling as the section above (`rule:guide-sighash:profile-decision`).

**Enforced at.** `packages/tapscript/src/authorization.rs`, the `DimensionRefusal::LeavesInputSetOpen` row; and `packages/target-elements/src/authorization.rs`, the `UnreviewedGround::TheSelectedProfileRefusesIt` row.

**Revising this exclusion touches:** this section; the refusals table in the owner sighash review together with the paragraph that draws the spent-outputs consequence from it; the profile-decision ruling; the refusal row `LeavesInputSetOpen` and its arm in `selected_owner_profile`; the unreviewed-ground row and the unestablished table entry in the target's authorization module; the spent-outputs dimension's own required typing, which the review derives from this refusal and which would need re-deriving rather than re-asserting; the two profile invariants; the capability test that separates the three unreviewed grounds; and the recomputed disposition.

## The annex · `rule:exclusions:annex`

**Excluded.** The profile refuses the annex. No witness this workspace builds carries one, and a signing request declaring one is refused rather than accommodated.

**Ground.** The adopted profile refuses the annex, on three grounds recorded together: this arc's witnesses carry none, an annex is non-standard for relay, and a profile permitting one would have to say what it may contain (`rule:guide-sighash:profile-decision`). The refusal buys a constant: with no annex the spend-type byte is `0x02` for every candidate this arc produces, and term 15 of the message is absent entirely (`tab:sighash-review:unnamed-terms`), so two message terms become values a test asserts rather than inputs a builder supplies.

**Enforced at.** `packages/transaction/src/live_census.rs`, the `OwnerCensusRefusal::AnnexDisagreement` row, which carries the spend-type byte the declared annex recomputes to rather than merely naming the disagreement.

**Revising this exclusion touches:** this section; the annex-disposition recommendation and the ruling in the owner sighash concept; the unnamed-terms table in the owner sighash review, where term 13 is a constant and term 15 is absent; the `AnnexDisagreement` row and its raise site in the live census; the spend-type constant the census recomputes against, and the constant's own assertion, which is written as a recomputation precisely so that a recomputation that stopped depending on the annex would fail rather than pass; the test `a_declared_annex_is_refused_with_the_spend_type_it_recomputes_to`; the exhaustiveness guard `every_refusal_variant_is_reached_by_a_test_in_this_file`, which would need a new entry for any variant this change added; and every recorded 64-byte weight measurement, since an admitted annex changes the witness the measurements were taken over.

## Non-default sighash type bytes · `rule:exclusions:type-byte`

**Excluded.** The profile admits the default hash-type byte alone. The byte `0x01` and the whole `0x8x` family are refused, and with them the 65-byte signature width that carries a trailing type byte.

**Ground.** The target is wider than the profile: the reviewed interpreter admits `0x00` through `0x03` and `0x81` through `0x83`, and the profile narrows that to one byte (`rule:guide-sighash:profile-decision`). The narrowing is not cosmetic, because a 65-byte signature is one whose trailing byte is the hash type and the target refuses a trailing zero, so the default and `0x01` are two different profiles rather than two spellings of one. A returned byte that disagrees is therefore a refusal and not a variant: the two produce different messages, and a report accepting both would be naming a profile it did not hold to. The bytes narrower than the default are refused by the two arguments already recorded above, since they are the single-output and input-extension commitments under another name.

**Enforced at.** `packages/transaction/src/live_census.rs`, the `OwnerCensusRefusal::TypeByteOutsideProfile` row for the byte and the `SignatureWidthOutsideProfile` row for the width the byte implies.

**Revising this exclusion touches:** this section; the admissible-hash-types table and the ruling in the owner sighash concept; the unnamed-terms table in the owner sighash review, where term 1 is a constant; the two census rows and their helper raise sites; the profile's type-byte and signature-width constants; the accepted-result checking that reads the returned byte and drops it rather than storing it, which is deliberately field-free so that a second opinion has nowhere to live; the tests `the_profile_checks_the_returned_type_byte_rather_than_recording_it`, `a_returned_type_byte_outside_the_profile_is_a_refusal_and_not_a_variant`, `the_profile_checks_the_returned_signature_width` and `a_returned_authorization_of_the_other_width_is_refused`; the refusal exhaustiveness guard; and every recorded 64-byte weight, which a 65-byte profile would falsify.

## Key-path spends · `rule:exclusions:key-path`

**Excluded.** Script path only. The candidate constructor offers no accepted key-path escape, and the internal key is a published unspendable point rather than a key anyone holds.

**Ground.** The internal key must be a deterministic, publicly auditable point with no known private scalar, and five candidate sources are named and excluded by the policy rather than left unused: an operator key, a release key, a generated-then-discarded secret, a test key, and a mutable deployment key (`rule:state-constructor:internal-key`). The execution guides carry the same rule with its consequence: there is no accepted key-path escape, and every target vector includes an attempted key-path spend required to be rejected or unconstructible (`rule:guide12-exec:no-keypath`), inherited unchanged by the live-transfer constructor (`rule:guide13-exec:internal-key`). The profile follows the shape rather than the other way round: three message terms exist for a script-path spend that do not exist for a key-path one, and the profile admits the script path alone (`rule:guide-sighash:spend-path`). What the evidence establishes is deterministic derivation and the absence of a generation step; discrete-log hardness is not established and stands as a named residual, which is why the policy variant states its assumption in its own name.

**Enforced at.** `packages/tapscript/src/bundle.rs`, the `InternalKeyPolicy::UnspendableWithResidualDiscreteLogAssumption` row. The enum has one variant, so an operator key, a release key, a wallet key, a generated-and-discarded key and a caller-selected key are unrepresentable rather than merely unselected, and the exclusion is enforced by the shape of the type rather than by a check that could be skipped.

**Revising this exclusion touches:** this section; the internal-key policy in the state-constructor research with its excluded-sources list and its evidence boundary; the no-key-path and internal-key rules in the Guide-12, Guide-13 and Guide-14 execution documents; the spend-path rule in the owner sighash concept and the internal-key remark in the owner sighash review, since the internal-key dimension is typed as carried by the spent outputs rather than by a term of its own; the `InternalKeyPolicy` enum, its single variant, and the two construction sites in the bundle and the live constructor; the unspendable-internal-key bundle symbol, which is resolved at link rather than minted, so a policy change is a link-time change and not only a type-level one; the tests `the_inherited_policies_are_the_compact_ash_constructors_own`, `the_constructor_binds_what_the_rule_lists_and_nothing_that_would_weaken_it` and `the_bundle_is_a_candidate_and_carries_its_outstanding_lifecycle`; and the discrete-log residual carried in the Phase-5 residual set (`sec:phase5:residuals`), which has no label of its own and would have to be re-argued rather than re-cited.

## Peg-ins · `rule:exclusions:pegin`

**Excluded.** A peg-in is outside the candidate. Byte strings carrying a peg-in marker on an input's outpoint, or a non-empty peg-in witness field, are refused by the decoder rather than decoded and ignored.

**Ground.** The candidate transaction this workspace constructs consumes receipts of an already-issued asset and creates destinations of the same asset. A peg-in is a different origin for value, with its own proof material and its own trust assumptions about a second chain, and admitting one would mean the conservation the covenant checks was over a quantity part of which entered from outside the model. The exclusion is enforced at the decoder because it is a property of admissible bytes rather than of a builder's intent: a construction that never builds a peg-in still has to refuse one offered to it, or the refusal is an assumption rather than a check. This election is recorded doc-side here for the first time; before this register its only statement was the decoder row's own doc comment and a parser bullet in the Guide-14 concept, which is why the ground is written out rather than cited.

**Enforced at.** `packages/transaction/src/error.rs`, the `TransactionRefusal::PeginInputRefused` row, raised at two sites in `packages/transaction/src/bytes.rs`: the outpoint's peg-in flag bit, and the peg-in witness field of the input witness.

**Revising this exclusion touches:** this section; the parser-rejects list in the Guide-14 concept, which names unsupported peg-in fields without a ground; the `PeginInputRefused` row and its two raise sites; the input-witness decoder, whose peg-in field is currently required empty rather than parsed, so admitting a peg-in is a decoding change and not a predicate change; the test `issuance_and_pegin_markers_are_refused_rather_than_ignored`, which reaches the outpoint-marker site only, the witness-field site being uncovered today and named here so that a revision does not mistake one test for two; the conservation argument the covenant checks, which assumes every source of the asset is a consumed receipt; and the transaction refusal vocabulary, which has no exhaustiveness guard, so a variant added or removed here is not caught by a census the way the census refusals are.

## Issuance-bearing transaction bytes · `rule:exclusions:issuance-bytes`

**Excluded.** Byte strings carrying an issuance are outside the candidate, in both places the wire form can carry one: the issuance marker on an input's outpoint, and the issuance proof fields of an input witness.

**Ground.** The candidate consumes receipts and creates destinations of an asset already issued; an issuance creates asset units inside the transaction being authorized, which is a second source of the conserved quantity, and the same argument that excludes a peg-in excludes it. The decoder is where the exclusion belongs, because the claim being protected is about what bytes may be admitted rather than about what a builder intends to write. The exclusion is the byte-level half only; the signing-request half is the section below, and the sighash-dimension half is the section after that.

**Enforced at.** `packages/transaction/src/error.rs`, the `TransactionRefusal::IssuanceInputRefused` row for the outpoint marker and the `IssuanceProofRefused` row for the witness proof fields, raised in `packages/transaction/src/bytes.rs`.

**Revising this exclusion touches:** this section; the two sections below, which are the other two faces of the same election; the parser-rejects list in the Guide-14 concept; the `IssuanceInputRefused` and `IssuanceProofRefused` rows and their three raise sites; the input-witness decoder, whose two issuance proof fields are required empty rather than parsed; the test `issuance_and_pegin_markers_are_refused_rather_than_ignored`, which reaches the outpoint marker; the fact that `IssuanceProofRefused` is reached by no test at all, recorded here rather than left to be discovered, since a revision that assumed coverage would be revising an unexercised row; the transaction refusal vocabulary's lack of an exhaustiveness guard, which is why that gap is invisible today; and the conservation argument the covenant checks.

## Issuance-bearing signing requests · `rule:exclusions:issuance-requests`

**Excluded.** A signing input that declares an issuance is refused by the owner census. The census carries no field for an issuance and does not acquire one.

**Ground.** The census's silence about the input-witness vector is a claim, and it rests on the precondition that no input bears an issuance; the source review put that on this arc's desk by name, saying an issuance-bearing candidate needs either a census field for the input-witness issuance proofs or a typed refusal saying the profile does not admit that shape (`rule:sighash-review:census-consequence`). The refusal is the answer chosen, and it is what makes the precondition checked rather than assumed. A field would have been the other answer and was not taken, because carrying issuance proofs in the census would mean the recomputed message read them, which is a commitment this profile does not make.

**Enforced at.** `packages/transaction/src/live_census.rs`, the `OwnerCensusRefusal::IssuanceBearingInputRefused` row, raised where the census is assembled.

**Revising this exclusion touches:** this section; the census-consequence rule in the owner sighash review, which states both answers and would need re-reading, not only re-wording; the issuance disposition type in the live census, whose documentation names this refusal as the precondition's check; the `IssuanceBearingInputRefused` row and its raise site; the census's absence of an input-witness field, which is the shape the refusal protects and which a revision would have to add before the refusal could be relaxed; the tests `an_issuance_bearing_input_is_refused` and the exhaustiveness guard `every_refusal_variant_is_reached_by_a_test_in_this_file`; the message construction, which forms the two issuance terms from the input count alone and would have to read an issuance subject instead; and the section below, whose ruling this refusal now also enforces.

## The issuance sighash dimension · `rule:exclusions:issuance-dimension`

**Excluded.** The issuance dimension of the owner sighash message is refused. It was typed as required until the Wave-4 verdict, and the owner has re-typed it from required to refused, so it joins the single-output and input-extension dimensions as a refusal with content rather than remaining a required dimension nothing could establish.

**Ground.** The verdict stopped on the one required dimension no candidate this arc builds can exercise (`rule:guide-sighash:profile-decision`). The message's two issuance terms hash one zero byte per input for every issuance-free candidate, so agreement between a recomputed digest and an accepted transaction exercises the input count and nothing about any issuance, and the input count is already carried by the all-inputs dimension. A term computed without consulting the dimension's own subject cannot disagree with the target about that subject, so no number of agreeing digests checks the model about it. Meanwhile the census refuses an issuance-bearing signing request (`rule:exclusions:issuance-requests`) and the decoder refuses issuance-bearing bytes (`rule:exclusions:issuance-bytes`), which made the required typing the one layer promising evidence the other two layers refuse to admit. The owner's election resolves that disagreement in favour of the two layers that refuse.

**Enforced at.** Three rows enforce the exclusion's subject and two more enforce its typing, and all five cite this tag.

The subject rows are the rows of the two sections above, which is why they cite this tag as well as their own: `OwnerCensusRefusal::IssuanceBearingInputRefused` in `packages/transaction/src/live_census.rs`, and `TransactionRefusal::IssuanceInputRefused` together with `IssuanceProofRefused` in `packages/transaction/src/error.rs`.

The typing rows are the follow-up sighash wave's, which has landed: `packages/tapscript/src/authorization.rs`, the `DimensionRefusal::SubjectRefusedByTheCensusAndTheDecoder` row, which is the profile's typed reason for refusing the dimension and names the three subject rows in its own text; and `packages/target-elements/src/authorization.rs`, the `UnreviewedGround::TheSelectedProfileRefusesIt` row, which the issuance dimension now carries alongside the single-output and input-extension ones. The profile's role assignment gives `SighashDimension::Issuance` the refused role, the required set is six, and the coverage map's `ProtectedDatum::IssuanceFields` entry names `SighashDimension::AllInputs` — a fourth citation sits at that entry, because moving the datum is the one consequence this re-typing had that the internal key's did not.

**Revising this exclusion touches:** this section and the two above it; the post-verdict ruling in the owner sighash concept; the refusals table in the owner sighash review, which names two refused dimensions and would become three, and which the landed re-typing has not edited — the profile refuses three dimensions and that table describes the two the target offers as branches, which is a distinction a revision has to keep rather than a discrepancy to smooth; the five enforcing rows named above with their raise sites and tests; the profile's role assignment and its required-set count, which is asserted as the literal six in three places; the coverage map entry for the issuance fields and the invariant that no protected datum rests on a refused dimension, which is what the re-assignment was made to keep true; the recomputed disposition, which is `Established` and would not be if the dimension returned to the required set; the tests `the_profile_refuses_three_dimensions_each_on_a_stated_ground`, `re_typing_the_issuance_dimension_moves_one_protected_datum_and_names_where`, `the_reviewed_contract_establishes_the_profile_over_a_six_member_required_set`, `each_unreviewed_dimension_records_which_kind_of_unreviewed_it_is` and the four cross-package assertions in `packages/vectors/tests/sighash_verdict.rs`; the `UnreviewedGround::NoCandidateThisArcBuildsCarriesTheSubject` variant, which this re-typing left carried by no dimension and which is kept deliberately, so a revision returning the dimension to required would restore its one occupant rather than reintroduce a vocabulary member; and the five residual vocabularies across the tapscript, linker, transaction, vectors and target-elements-conformance packages, whose unreviewed-profile residual this re-typing cleared and whose wording now rests on the dimension being refused exactly as it used to rest on its being required.

The fifth vocabulary is named separately here because it was missed, and a reviser should not have to find it a second time. The owner sighash concept says the residual is carried in four vocabularies; that was a census of the vocabularies known when it was written and not a cap on how many exist, and the conformance package's `CaseResidual::ProfileUnreviewed` in `packages/target-elements-conformance/src/owner_authorization.rs` carried the same claim on every owner-authorization case. It clears on the same recomputed verdict as the other four. It is also the site where the claim mattered most, because the failure that census is shaped against is precisely the one an unestablished profile leaves open: under a narrower profile a mutation case is a transaction the target accepts, and the evidence it produced would be worth nothing. Two things a revision must carry with it. Restoring the dimension to the required set restores this carrier along with the other four. And clearing it discharged no case, which the census proved rather than the prose asserting: this vocabulary refuses a case with nothing outstanding, so removing the profile residual and leaving the set empty made the census stop validating and name the valid case as one claiming to be runnable. What was outstanding had not become nothing. The profile residual had been carrying two claims — the profile gap, and the fact that no run had produced a verdict — and only the first was cleared, so the second is now `CaseResidual::NoObservedTargetVerdict`, a member this wave minted because the site's own rule required the claim to be named before the old carrier could go. A revision touches that member too: it is cleared by an observed run and by nothing else, and in particular no further review can clear it.

The register no longer records work owed here. The profile types the dimension refused, the disposition recomputes to established, and the residual is cleared in all five vocabularies — which is the honest state of the tree, as the owed wording was before it.

## Asset blinding and surjection proofs · `rule:exclusions:asset-blinding`

**Excluded.** Blinded assets. The one confidential form this workspace constructs is the hybrid form, a committed value paired with an explicit asset, whose surjection-proof field the target requires to be empty. A surjection proof in decoded bytes is refused, a materializer returning one is refused, and a protocol member whose asset field is a commitment is refused.

**Ground.** The target accepts the selected hybrid form: a confidential value paired with an explicit asset uses the unblinded asset generator, requires a range proof, and requires the surjection-proof field to be empty (`sec:guide-ctf:target-boundary`). The first implementation slice fixes every protocol asset blinder at zero, so no output carries a surjection proof at all (`rule:guide-ctf:predecessor-slice`), and the materializer is required to reject any confidential-asset result (`def:guide-ctf:materializer`). The decoder's refusal is unconditional and that is the form-conditional answer rather than an exception to it, because the unblinded-generator case is the only case this workspace builds and a byte string carrying a surjection proof is a blinded-asset form nothing here produces. The asymmetry with the range proof is deliberate and recorded at the refusal: the range-proof refusal is conditional on the output's own value field in both directions, while the surjection refusal is not.

**Enforced at.** `packages/transaction/src/error.rs`, the `TransactionRefusal::SurjectionProofRefused` row for decoded bytes; and `packages/transaction/src/live_materialize.rs`, the `MaterializationRefusal::UnexpectedSurjectionProof` row for a materializer that returns a proof for a form requiring the field empty, and the `ConfidentialProtocolAsset` row for a protocol member whose asset field is a commitment.

**Revising this exclusion touches:** this section; the target-boundary section, the predecessor-slice rule and the materializer definition in the confidential funding concept, together with the mission's fixed output form; the sighash-boundary rule in the same concept, which requires the exact range-proof and surjection-proof fields covered by the profile to be final before any receipt owner signs, so an admitted surjection proof moves the bytes an owner binds to; the `SurjectionProofRefused` row with its unconditionality argument and its raise site in the output-witness decoder; the `UnexpectedSurjectionProof` and `ConfidentialProtocolAsset` rows with their raise sites in the per-output materialization and the preflight; the sibling rows `NonzeroProtocolAssetBlinder` and `ProtocolAssetMismatch`, which enforce the same zero-blinder election from the other side; the tests `a_surjection_proof_is_refused_for_either_value_form`, `a_surjection_proof_is_refused_for_the_hybrid_form`, `an_unexpected_surjection_proof_is_refused` and `a_committed_protocol_asset_and_a_nonzero_asset_blinder_both_refuse`; the encoding round-trip requirement that empty surjection proofs travel exactly; and the two upstream frictions recording that no reviewed interface accepts a blinding seed and that blinded inputs cannot be consumed to a fully explicit output set.

## The wallet's own blinding path · `rule:exclusions:wallet-blinding`

**Excluded.** The target's own blinding machinery is not used to produce this workspace's confidential outputs. Calling the raw blinding RPC, retrying ordinary wallet blinding until an output happens to look useful, and mutating a fully blinded asset back to explicit after proof construction are all excluded.

**Ground.** No reviewed stock RPC produces the selected form. The common path draws fresh value and asset blinders, blinds the asset, creates a fresh ephemeral nonce, and generates both a range proof and a surjection proof; both the wallet and raw blinding entry points enter that common path, and none of their reviewed parameters selects confidential value with an explicit asset or supplies deterministic blinding and nonce inputs (`sec:guide-ctf:target-boundary`). The three named workarounds are rejected by the charter in the same paragraph, so the exclusion is a decision and not a discovery. The positive requirement that follows is determinism: the ceremony has a proven field-identical rerun and stock blinding uses fresh randomness, so it cannot satisfy that contract (`rule:guide-ctf:determinism-decision`). This exclusion is therefore the only one in this register whose enforcement is the existence of a component rather than a refusal row — the deterministic materializer is what the rejection of the wallet path required to be built, and its module documentation is where the tag is cited.

**Enforced at.** `packages/transaction/src/live_materialize.rs`, the module documentation of the transaction-wide confidential materializer, which is the only complete-private construction entry point there is.

**Revising this exclusion touches:** this section; the target-boundary section of the confidential funding concept, where the reviewed RPC finding and the three rejected workarounds sit in adjacent paragraphs; the determinism decision and its byte-identity recipe, whose typed refusals and bounded deterministic search exist because hidden randomness is excluded; the materializer definition, which replaces the per-output capability rather than extending it; the materializer module documentation carrying the citation, and with it the whole entry point, since the exclusion is enforced by that component existing and being the only route; the injected-cryptography argument in the same module, because a wallet-blinded output would arrive with proofs from an origin the independence rule does not admit; the per-output value capability, which is retired by scope for this lane and still serves the lane it describes; the field-identical rerun evidence, which is the property the exclusion was taken to preserve; and the reference material status of the generic confidential-conservation workload, which uses the fully confidential path and reports fixture-only inputs.

## What this register does not say · `rule:exclusions:nonclaims`

An exclusion here is this workspace's election, never a verdict about the target. Every feature named above is one the target supports; nothing in this register claims otherwise, and no section is evidence about a chain.
