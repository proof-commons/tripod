# Guide 14 conceptual review C — standard mutation algorithms

## §1. Question restated in my own terms

The governing question is whether Guide 14 presents STATE at the semantic top as one genuinely mutable canonical state variable, while realizing each mutation at the UTXO back end as a tracked predecessor-to-successor transformation with the full guarantees of recognizable standard techniques.

This review therefore does four things:

1. identifies the standard formalisms latent in the guide: labeled transition systems, deterministic partial transitions made total with typed errors, persistent authenticated data structures, event-sourced replay, focused updates, compare-and-swap, hash-linked histories, covenants, and commitment-chained single-use seals;
2. maps each Guide-14 mechanism to those formalisms and marks their canonical obligations as **ADOPTED**, **WEAKENED**, or **OMITTED**;
3. decides whether “change maturity and mechanically preserve the complement” proves the usual lens laws; and
4. identifies places where a named standard form would be stronger or simpler than the guide's collection of private checks and reports.

The review is conceptual. It does not treat absence of a particular implementation spelling as a defect, and it does not review prose style or repository conventions. The guide was read at `0.6.145-dev` in a clean, read-only worktree. Repository substrate was consulted only to understand the intended semantic model; in particular, the existing model already has a pure invariant-wrapped transition API, a bound predecessor/request/successor object, record-update maturity semantics, derived transition certificates, and full root-cursor replay (`packages/model/src/transition.rs`, `ops/maturity.rs`, `certify.rs`, and `invariant.rs`).

## §2. The guide's actual design as I read it

### 2.1 Semantic top

The guide treats STATE as a singleton canonical root, not as any output that happens to carry STATE-shaped bytes. An accepted operation must consume exactly the current STATE root, create exactly one successor, record the succession edge, and exclude other STATE-like and other-root effects (Guide §§1.3, 2.2–2.6). The request selects only an announcement cycle; it does not select a predecessor, successor, program, nonce, root cursor, or operator (Guide §2.3).

The semantic value is intended to be one typed record whose complete field census comes from the authoritative typed source. Maturity is a closed sum type. A separate representation nonce is explicitly erased by semantic projection and retained only for construction evidence (Guide §§1.1, 1.5, 3.1, 6.1–6.3). This is a sound abstract-data-type boundary: protocol meaning and target spelling are not conflated.

The semantic step is a typed function

```text
announce_maturity(predecessor, announced_cycle, bounds)
    -> successor or MaturityTransitionRefusal
```

It checks the predecessor phase and lead interval with checked arithmetic, changes maturity, copies the complement, and produces neither a representation nonce nor a partial successor (Guide §§1.4, 1.11, 6.5). The model and realization are supposed to agree, and expected semantics may not be generated by the back end (Guide §§15.1, 15.3; Wave 1).

### 2.2 Canonical representation

Metadata has a domain separator, schema revision, fixed field order and widths, byte order, closed discriminants, reserved-field rules, and trailing-byte rejection. The guide requires byte stability after successful decoding and a unique encoding for a fixed semantic value plus representation nonce (Guide §6.4). Malformed bytes, invalid transition conditions, and representation failures are placed in a closed refusal vocabulary (Guide §6.6).

The nonce is then ground deterministically from zero. The first value satisfying fixed branch order and target tweak definedness is canonical; semantic invalidity is never repaired by search, and exhaustion is a typed failure (Guide §§5.3–5.4, 6.3, 9.8, 12.5).

### 2.3 Concrete consume/reconstruct step

The target representation is a two-part Taproot construction: a dynamic, always-aborting metadata commitment leaf beside one exact linked static operation subtree (Guide §§5.2, 9.2–9.4). A maturity spend authenticates the consumed program from predecessor metadata, nonce, schema, static subtree, leaf version, internal key, tweak relation, and actual input program. It derives successor semantic metadata rather than accepting it independently, reuses the authenticated static subtree, validates the first canonical successor nonce, reconstructs the successor program, and compares it with output 0 (Guide §§1.7, 9.5–9.6, 10.5, 10.7).

The transaction layer obtains a validated current-STATE view, freezes the exact predecessor outpoint and spent output, fixes the sole successor output, finalizes all protected bytes, and only then requests operator authorization. Post-finalization mutation is unrepresentable or refused (Guide §§12.1–12.8, 13.1–13.4). Optional sponsors are disjoint and semantically opaque (Guide §§1.13, 10.9, 12.1–12.2).

### 2.4 Evidence and recovery

The guide intentionally keeps semantic safety, constructor continuity, root history, target acceptance, public recovery, and resources as separate conjuncts (Guide §§1.14, 14.3–14.8). Constructor continuity records both metadata-dependent constructions and exact static-root equality (Guide §14.5).

Root history is an ordered typed edge sequence. Each edge must begin at the current cursor, name the operation, bind its certificate to the target transaction, and validate before the cursor moves. For Guide 14 the tested sequence has one edge from a synthetic predecessor; no prior genesis history is claimed (Guide §§5.7, 14.6, 17.1). Native evidence is bound to network, genesis, block hash and height, transaction, outpoints, target contract, bundle, and ABI. A reorg makes the observation stale (Guide §17.2).

Public recovery starts from the accepted transaction's public witness and outputs. A process without creator-private state must locate and byte-check the transaction, decode predecessor data, run the typed transition, recover or derive the canonical nonce, reconstruct the successor program, and compare it with output 0 (Guide §§1.8, 5.1, 14.7). Wave 10 is assigned both the root-edge and recovery reports.

## §3. Standard concepts and obligation mapping

### 3.1 Survey of the standard forms

**Labeled transition system and abstract state machine.** A system is a set of states, labeled steps, and a transition relation. For a deterministic operation the relation is normally presented as a partial function. A typed `Result` can make the API total: every typed input terminates with either the unique successor or a closed error. Canonical obligations are a defined state/input/environment domain, deterministic results, termination, invariant preservation, atomic failure, and compositional traces.

**Refinement or forward simulation.** When an abstract state machine is compiled to a different concrete machine, the standard bridge is an abstraction relation. Every accepted concrete step must simulate one permitted abstract step, preserve the relation afterward, and introduce no extra behavior. If implementability is claimed, every supported abstract step must also have a concrete realization, subject to explicitly stated environmental assumptions. This is the usual compiler-correctness shape for the owner's two levels.

**Persistent functional data structure and path-copying.** An update retains the old value, reuses untouched structure, and reconstructs only the path from the changed focus to the root. In an authenticated Merkle structure, unchanged subtree commitments are shared and changed ancestors are rehashed. Obligations include immutable old versions, exact sharing of the complement, canonical shape/order, a binding commitment, and bounded update cost.

**Event sourcing and append-only replay.** The log is the source of truth; current state is a deterministic fold from a trusted origin or a versioned snapshot plus a complete suffix. Canonical obligations include immutable ordered events, stable identities and deduplication, complete and gap-free replay, validation before state advancement, snapshot/log position binding, schema evolution, crash-safe resume or idempotency, and a defined response to forks or log truncation.

**Lens or focused update.** For getter `get` and setter `put`, the two laws named in the question are:

```text
GetPut: put(s, get(s)) = s
PutGet: get(put(s, v)) = v
```

Many accounts also require `PutPut`: the last write wins. A record-field lens additionally satisfies a frame property: the complement of the focused field is unchanged. A guarded one-shot protocol transition is not itself a total lens; it can use a lawful record lens internally after its guard succeeds.

**Compare-and-swap and optimistic concurrency.** A client reads value plus version, computes a successor, and atomically commits only if the version still matches. Obligations are a value-bound version token, atomic compare and swap, conflict detection, no lost updates, ABA resistance, a linearization/finality rule, and defined retry/idempotency behavior.

**Hash-linked history and authenticated data structure.** A verifier must have canonical, domain-separated encodings; binding hashes under named collision/second-preimage assumptions; an authenticated root or checkpoint; membership and update evidence; and version or chain-context binding. Hashes authenticate commitments, not data availability or canonical chain selection.

**Covenant, state chain, and commitment-chained single-use seal.** A covenant constrains how a UTXO may be spent and which successor may be created. A commitment-chained single-use seal places the current state commitment in a spend-once output; closing it atomically opens the uniquely constrained successor commitment. A statechain, in the narrower established sense, transfers off-chain control of an existing UTXO and is not what Guide 14 implements. Guide 14 is best named a recursive covenant over a commitment-chained single-use seal.

### 3.2 Canonical root plus typed metadata — abstract data type and authenticated state commitment

| Canonical obligation | Status | Guide evidence and judgment |
|---|---|---|
| One authoritative semantic domain and field census | **ADOPTED** | Typed Rust is authoritative; the complete census must be found rather than guessed (Guide §§1.1, 3.1, 6.1). |
| Singleton/current root invariant | **ADOPTED per selected chain prefix** | Exactly one predecessor and successor, exact root roles, and no lookalikes are required (Guide §§1.3, 2.2–2.5, 10.2–10.3). Global chain canonicality is considered under root history below. |
| Semantic/representation abstraction function | **ADOPTED** | The nonce is a separate type, erased semantically and retained concretely (Guide §§1.5, 6.3). |
| Canonical grammar and fail-closed decoder | **ADOPTED** | Domain, revision, order, widths, discriminants, reserved fields, and trailing bytes are fixed (Guide §§6.2, 6.4). |
| Both codec round trips and semantic injectivity | **WEAKENED** | `encode(decode(b)) = b` is stated, but `decode(encode(x)) = x` for every valid pair and “different semantic pairs encode differently” are not explicit (Guide §6.4). Deterministic encoding is weaker than injective encoding. |
| Binding authenticated commitment under named assumptions | **OMITTED** | The guide specifies exact Taproot hashing and does name the NUMS discrete-log residual, but it does not state the collision/second-preimage and domain-separation assumptions on which metadata-leaf and static-root equality rely (Guide §§5.5, 9.3–9.6, 14.5). |
| Constructor-level canonical representation | **ADOPTED** | First admissible nonce, fixed branch side, strict policy, and later-nonce negatives are explicit (Guide §§5.3–5.4, 12.5, 16.6–16.7). |

### 3.3 Single transition function — deterministic partial state machine lifted to a total result

| Canonical obligation | Status | Guide evidence and judgment |
|---|---|---|
| Closed typed state, request, and error domains | **ADOPTED** | Closed maturity, typed cycle/bounds, typed metadata, and closed refusals are required (Guide §§6.1–6.6). |
| Total terminating decision procedure | **ADOPTED at the API level** | Checked arithmetic and `Result` cover invalid inputs; no partial successor is returned (Guide §§1.11, 6.5). |
| Deterministic/pure successor for fixed inputs and protocol parameters | **WEAKENED** | The signature is structurally pure, but the semantic determinism law is not stated; Guide §7.5 states determinism for compiler plans, not this transition. The authority/version of the supplied `bounds` must be bound as part of the transition context. |
| Invariant preservation | **WEAKENED** | Model/realization conformance and valid-world fixtures are required (Guide §§15.1, 15.3; Wave 1), but no universal invariant-preservation obligation is stated for the new metadata transition. |
| Atomic failure/no partial state | **ADOPTED** | The function returns a whole successor or a refusal, and representation grinding begins only after semantic success (Guide §6.5). |
| Abstract-to-concrete refinement | **OMITTED** | Relation censuses, carrier closure, reports, and vectors are present (Guide §§7.2–7.4, 11.5, 14), but no abstraction relation or forward-simulation obligation says that every accepted concrete step is exactly one semantic step. |
| Sequential composition/trace theorem | **OMITTED by scope** | Only maturity announcement is implemented and later STATE operations/migration remain outstanding (Guide §§2.7, 17.3). This is honest, but it prevents a general state-machine guarantee. |

The standard name is therefore “a deterministic guarded state transition with typed failures,” not merely “one function.” The existing model's invariant-wrapped `execute` and deterministic `bind_execution` are close to the standard form; Guide 14 should state how the new metadata function refines that already-existing state machine rather than leave conformance as a collection of fixtures.

### 3.4 Metadata refusals — total parser/validator with an algebraic error type

| Canonical obligation | Status | Guide evidence and judgment |
|---|---|---|
| Fail closed on unknown or malformed input | **ADOPTED** | Unknown tags/schema, wrong lengths, reserved fields, and trailing bytes refuse (Guide §§6.2, 6.4, 6.6). |
| Closed exhaustive error algebra | **ADOPTED** | The vocabulary is closed, and every variant needs a test or an unreachability proof (Guide §6.6). |
| No artifact on failure | **ADOPTED** | Decoder and transition return no partial successor (Guide §§6.4–6.5). |
| Layer-specific errors | **WEAKENED** | One initial vocabulary mixes codec faults, semantic-transition faults, and constructor-search faults. Standard parser, transition, and construction sums would preserve ownership more cleanly (Guide §6.6). |
| Deterministic precedence for multiply malformed inputs | **OMITTED** | The guide does not define whether refusal identity is stable when several predicates fail. This matters only if refusal identity becomes protocol or evidence data; otherwise the safer standard is to keep it non-normative. |

### 3.5 Per-field copy-through — guarded focused update, not a lawful lens as written

| Lens/focused-update obligation | Status | Guide evidence and judgment |
|---|---|---|
| `PutGet` for an admissible announcement | **ADOPTED as a requirement** | The successor maturity must equal the requested cycle (Guide §§1.4, 2.4, 6.5). |
| Complement/frame preservation | **WEAKENED as proof** | Exact equality of every other field is required, schema-derived copying is preferred, and each field gets a mutation negative (Guide §§1.4, 10.5, 16.3). Wave 1 promises per-field tests, which are examples, not a law over all values or a proof that schema layout and semantic projection commute. |
| `GetPut` | **OMITTED/inapplicable to the transition** | Putting the current `Unannounced` maturity is not an allowed operation; the transition only writes `Announced`, so it cannot satisfy the law as an operation (Guide §§6.2, 6.5–6.6). |
| `PutPut` | **OMITTED/inapplicable to the transition** | A second announcement is explicitly refused, not overwritten (Guide §§6.5–6.6, 16.2). |
| Explicit optic domain for a guarded update | **OMITTED** | The guide does not separate the lawful record-field setter from the one-shot state-machine guard. |
| Semantic/byte-level commuting law | **WEAKENED** | Prefix/maturity/suffix reconstruction is strong path-copying, but the guide does not state that decoding the byte update equals applying the semantic update for every canonical input (Guide §10.5). |

The answer to the question's lens-law issue is therefore **no**. Copy-through tests establish selected frame examples and the useful half of `PutGet` on admissible requests. They do not establish `GetPut`, and the one-shot transition is intentionally incapable of satisfying it. The simpler standard design is to define a lawful generated lens or product decomposition for the `maturity` field, prove its laws once, and then define announcement as “check guard, use the lens to set `Announced(a)`.” The guard may remain partial while the record update is lawful.

### 3.6 Consume/reconstruct — persistent Merkle path-copying, recursive covenant, single-use seal, and CAS

| Canonical obligation | Status | Guide evidence and judgment |
|---|---|---|
| Immutable predecessor plus freshly reconstructed successor | **ADOPTED** | The predecessor UTXO is consumed and output 0 is constructed after semantic derivation (Guide §§2.2–2.4, 9.5–9.6, 12.5). |
| Path-copying/structure sharing | **ADOPTED** | The dynamic metadata leaf and ancestors change while the exact static subtree is reused (Guide §§5.2, 9.2, 9.6, 17.3). This is commitment sharing rather than physical in-memory sharing, which is the correct authenticated analogue. |
| Canonical tree shape and update path | **ADOPTED** | Fixed roles, branch side, stable tree construction, and first-nonce selection are required (Guide §§5.3–5.4, 9.2, 11.4). |
| Authenticate the exact predecessor read | **ADOPTED** | Outpoint, metadata, nonce, schema, subtree, key, tweak, and actual consumed program are bound (Guide §§9.5, 12.4, 13.1–13.2). |
| Atomically consume that version and create the successor | **ADOPTED relative to target consensus** | One transaction contains the sole STATE input and output; all bytes are frozen before signing (Guide §§10.2, 12.1–12.8). This is the CAS linearization candidate. |
| Conflict/stale-read exclusion | **ADOPTED on one chain prefix** | Stale predecessors and wrong current views are negative cases; an already-spent outpoint cannot be consumed again on the selected chain (Guide §§1.3, 16.8, 17.1). |
| ABA resistance | **ADOPTED on one chain prefix** | Outpoint identity plus exact program/metadata prevents a later equal semantic value from masquerading as the version originally read (Guide §§12.4, 13.1, 17.1–17.2). Reorgs remain a separate qualification. |
| No alternate covenant escape | **ADOPTED strongly** | Metadata leaf always aborts, key-path escape is not claimed, leaf/control/key/static-root substitutions reject, and no placeholder leaf is present (Guide §§9.3–9.6, 16.5–16.7). |
| Constructor success for every valid semantic state | **WEAKENED** | The bounded nonce search terminates but may return `RepresentationSearchExhausted` (Guide §§5.4, 9.8). This is a total decision procedure around a partial constructor, not total constructibility. |
| Linearization/finality and retry semantics | **OMITTED/WEAKENED** | The transaction is atomic within a chosen chain prefix, but Guide 14 specifies staleness after reorg rather than a finality rule, conflict retry, or idempotent resubmission contract (Guide §17.2). |

This is the guide's strongest standard-algorithm mapping. It should be named directly: **a recursive covenant implementing a commitment-chained single-use seal, using authenticated persistent path-copying and the predecessor outpoint as a CAS version token**. It is not a statechain in the narrower off-chain-control-transfer sense.

### 3.7 Root-history edge sequence — branch-relative replay log over a hash-linked substrate

| Event-log/history obligation | Status | Guide evidence and judgment |
|---|---|---|
| Ordered typed events/edges | **ADOPTED** | The report consumes an ordered typed edge sequence (Guide §§14.6, 17.1). |
| Validate before advancing state | **ADOPTED** | The cursor advances only after predecessor, successor, certificate, operation, and unrelated-root checks (Guide §17.1). |
| Duplicate/gap/intermediate-corruption detection | **ADOPTED for the supplied sequence** | Duplicate/missing edges and cursor restoration after a bad intermediate edge are mandatory negatives (Guide §§1.3, 16.8, Wave 10). |
| Replay from trusted origin or a fully bound snapshot | **WEAKENED by explicit scope** | The tested history begins at a synthetic predecessor and covers one edge; prior history is disclaimed (Guide §5.7). This is a local edge audit, not full event sourcing. |
| Event/log authenticity | **WEAKENED** | Network, genesis, block, transaction, and outpoints are recorded (Guide §17.2), but no inclusion proof, authenticated header chain, or explicit trusted-node contract is required. |
| Exactly-once global history | **OMITTED** | Exactly one edge is shown inside one selected sequence and chain prefix. Competing prefixes can each contain a locally valid edge until a chain-selection/finality policy chooses between them. |
| Reorg rollback and deterministic resume | **OMITTED** | A reorg stales evidence, but the guide does not specify rollback point, replay procedure, or replacement report semantics (Guide §17.2). |
| Snapshot/version and schema migration | **OMITTED by scope** | Static-subtree migration is forbidden and left to later work (Guide §§2.7, 17.3). No event schema evolution is specified. |

Accordingly, the mechanism is best described as a **checkpoint-bound transition-certificate replay for a supplied chain prefix**, not a complete event-sourced store. The repository's existing full root-history replay is a stronger standard reducer; Guide 14 can reuse its contract while truthfully limiting native evidence to the synthetic edge.

### 3.8 Public recovery — deterministic materialized-view reconstruction from public transaction data

| Recovery obligation | Status | Guide evidence and judgment |
|---|---|---|
| All reconstruction inputs are public and versioned | **ADOPTED in intent** | Witness, metadata schema, requested cycle, nonce, output position, leaf version, key policy, and static recipe/reference are listed (Guide §§1.8, 5.1). |
| Deterministic reducer and byte comparison | **ADOPTED** | Recovery derives semantic metadata and canonical construction and compares it to the actual output (Guide §§1.8, 14.7). |
| No creator-private or ambient dependency | **ADOPTED** | Creator memory, temporary files, and wallet descriptors are negative cases (Guide §§14.7, 16.13). |
| Authentic source inclusion and canonical chain selection | **OMITTED** | “Locate the accepted transaction” and record a checkpoint do not themselves provide a transaction-inclusion proof, authenticated header chain, or trusted-node assumption (Guide §§1.8, 17.2). |
| Independent implementation, not merely a separate process | **WEAKENED** | The report may come from an unrelated process **or** a process constrained to the public handoff. The same decoder/constructor code can therefore reproduce the same bug (Guide §14.7). |
| Static-subtree data availability | **WEAKENED** | An exact static-root reference is sufficient to reconstruct the output commitment, but not to inspect every committed leaf. The guide should distinguish commitment recovery from code availability (Guide §1.8). |
| Reorg-safe recovery/resume | **OMITTED** | Staleness is identified but recovery after staleness is not specified (Guide §17.2). |

This is strong deterministic reproducibility. It becomes independently authenticated public verification only after its chain source and trust anchor are specified.

## §4. Ranked findings

### 1. CONCEPT-BLOCKER — the guide never states the standard refinement theorem connecting its two levels

**Implicated sections:** Mission and thesis; §§1.1, 1.4, 6.5, 7.2–7.4, 9.5–9.6, 11.5, 14.3–14.7; Waves 1, 5, 8–10; §23.

The guide has nearly all the ingredients of a refinement proof but leaves them as separate censuses, target checks, reports, and observed test rows. The exit conjunction says that target acceptance, semantic equality, constructor continuity, root history, and recovery all matched for the exercised candidate. That does not state the universal compiler-correctness obligation required by the owner's doctrine: every concrete accepted STATE spend must correspond to exactly one permitted abstract mutation, and the successor commitment must represent the abstract successor under the same abstraction relation.

Without that relation, “single semantic function” and “consume/reconstruct” are two well-tested algorithms adjacent to one another, not a standard verified state-machine refinement. It also leaves ambiguity about the relationship among existing model `PoolState`, proposed realization `StateMetadata`, target metadata bytes, and the public current-STATE view.

**Recommendation:** define abstract state `A`, concrete state `C`, request `r`, abstraction relation `R(C,A)`, semantic transition `delta`, and concrete target step `tau`. Require a forward-simulation contract:

```text
R(C, A) and target_accepts(tau(C, r) = C')
    implies
delta(A, r) = Ok(A') and R(C', A')
```

Add concrete atomicity and unique-root conditions, and separately state supported-step completeness when claimed. Make every report a witness for a clause of this theorem, not a substitute for the theorem. Bind the protocol bounds/version into `R` or the transition context. Reuse the existing invariant-wrapped model execution and deterministic replay binding as the semantic side.

### 2. CONCEPT-BLOCKER — “exactly one valid edge” is only branch-relative unless chain selection and finality are part of the algorithm

**Implicated sections:** §§1.3, 5.7, 10.3, 12.4, 14.6, 17.1–17.2; Wave 10; §§21, 23.

The UTXO outpoint is an excellent version token and consensus prevents two spends on one chosen chain. Checkpoint binding also prevents silently reusing evidence after a reorg. But two competing chain prefixes can each contain a locally valid spend of the same predecessor. Recording block hash and declaring the other observation stale after the fact does not define which transition linearized, when it became canonical, or how dependent state rolls back and resumes.

Thus Wave 10 can establish “one valid edge in this checkpointed chain prefix,” not an unqualified global exactly-once history or a permanently canonical current root. This distinction is central to CAS, event sourcing, and state-machine replication.

**Recommendation:** either narrow every guarantee to the selected chain prefix, or add a named chain-selection/finality policy: trusted full-node active-chain view or authenticated headers, confirmation/finality threshold, the precise linearization point, rollback checkpoint, deterministic suffix replay, invalidation of dependent reports, and conflict/idempotent retry behavior. The chosen policy belongs in the root-history report's standing, not only in run provenance.

### 3. DESIGN-RISK — Wave 1 does not prove the lens laws it is being asked to stand for

**Implicated sections:** §§1.4, 6.5, 10.5, 15.5, 16.3; Wave 1; §20.4.

The transition proves the desired focus value for valid requests and demands equality of the complement. It cannot satisfy `GetPut`, because writing the predecessor's `Unannounced` value is not the operation, and it cannot satisfy `PutPut`, because a second announcement refuses. Per-field fixtures and mutation negatives do not change that. They also do not universally prove that byte slicing and semantic field projection commute.

The guide therefore has a guarded one-shot transition with a frame condition, not a lawful lens. Calling the tests lens-law evidence would overstate the result.

**Recommendation:** factor the design into (a) a lawful record-field lens or generated product decomposition for maturity and (b) a guarded announcement transition that invokes its setter after authorization and lead checks. State and test `GetPut`, `PutGet`, `PutPut`, complement preservation, and the codec commuting law for the lens. State separately that the protocol transition remains partial and non-repeatable.

### 4. DESIGN-RISK — bounded nonce retry gives termination, not constructor totality

**Implicated sections:** §§5.3–5.4, 6.3, 6.6, 9.8, 12.5, 16.7; Waves 4 and 7; §§21–23.

The guide commendably types `RepresentationSearchExhausted` and refuses to use nonce search to repair semantic invalidity. However, a finite search through `0..R_max` can still fail for a semantically valid state. That makes the constructor a partial semantic-to-target map wrapped in a total decision procedure. Calling this “tweak totality” risks importing the stronger guarantee that every valid semantic state has a concrete representation.

This gap also blocks the completeness half of the refinement theorem: a valid abstract transition may have no constructible successor under the configured bound.

**Recommendation:** rename the guarantee to “bounded deterministic canonicalization with explicit exhaustion,” or prove a total mapping. If the intended argument is cryptographic negligibility, state the hash/random-oracle assumption, bound, quantified failure probability, operational handling, and whether exhaustion is a consensus-level permanent refusal or a candidate-only construction failure.

### 5. DESIGN-RISK — public recovery proves reproducibility but not independently authenticated recovery

**Implicated sections:** §§1.8, 5.1, 14.7, 16.13, 17.2; Wave 10; §§21, 23.

All necessary constructor inputs are intended to be public, and comparing reconstructed bytes with output 0 is strong. But a separate process may reuse the same implementation, and the guide does not require a membership proof or name a trusted full-node interface and active-chain contract. An exact static-root reference also provides commitment reuse without necessarily providing the committed code.

Consequently the report shows absence of creator-private dependencies and deterministic reproduction; it does not, by itself, show independent source authenticity, implementation diversity, or static-subtree data availability.

**Recommendation:** decide which guarantee is intended. For reproducibility, rename it and bind the public handoff exactly. For independently authenticated recovery, require an independently implemented decoder/reducer or a differential oracle, an explicit chain trust anchor plus transaction inclusion evidence, active-chain/finality rules, and a data-availability rule for the linked static bundle.

### 6. DESIGN-RISK — canonical encoding and authenticated-constructor guarantees omit two standard obligations

**Implicated sections:** §§5.3–5.5, 6.4, 9.3–9.6, 12.8, 14.5.

The guide states the useful canonical-byte law `encode(decode(b)) = b`, but not the value round trip `decode(encode(x)) = x` or semantic injectivity. A decoder that maps two semantic values to the same bytes can satisfy the stated byte law. Likewise, equality of leaf/root commitments provides exact semantic binding only under named hash-domain and collision/second-preimage assumptions; the guide names the internal-key discrete-log residual but not these commitment assumptions.

**Recommendation:** require both codec round trips, semantic injectivity across distinct semantic-value/nonce pairs, and a schema/layout theorem for field slicing. Record the exact tagged-hash domain separation and collision/second-preimage assumptions in constructor evidence. Distinguish exact byte equality, equality of committed roots under assumptions, and equality of hidden subtree contents.

### 7. DESIGN-RISK — the root-history report is a one-edge audit slice, not a complete event-sourced history

**Implicated sections:** §§5.7, 14.6, 17.1–17.3; Wave 10.

The guide is honest that the synthetic predecessor proves no earlier history. Nevertheless, terms such as root-history replay and invalid-intermediate-edge resistance evoke the stronger event-sourcing obligation of a complete, gap-free fold from origin or a fully bound snapshot. For the native Guide-14 claim, only one supplied edge is required. No authenticated completeness proof shows that the report contains every relevant event between an origin/checkpoint and its cursor, and no schema-migration or replay-resume contract exists.

**Recommendation:** call the Guide-14 artifact a checkpoint-bound edge certificate or local history slice. If it is meant to seed future event sourcing, define a versioned snapshot position, complete suffix acquisition, deterministic reducer, gap/duplicate rules, reorg rollback, and migration policy now. The existing model's full root replay is a natural reference reducer.

### 8. OBSERVATION — the refusal vocabulary would be simpler as three standard error sums

**Implicated sections:** §§6.4–6.6, 9.8.

The initial vocabulary combines byte-decoding failures, semantic-transition failures, and constructor canonicalization failures. This is fail-closed, but it weakens ownership and makes stable error precedence harder.

**Recommendation:** use separate `DecodeError`, `MaturityTransitionError`, and `ConstructorError` sums, compose them at the orchestration boundary, and state whether exact error identity is normative. If it is normative, define precedence for multiply invalid inputs; if not, keep only success/failure normative.

### 9. OBSERVATION — the consume/reconstruct core already has a strong standard name and should use it

**Implicated sections:** §§1.3, 1.7, 5.2–5.5, 9, 10.2–10.8, 12, 17.1.

The core is not an improvised “mutable UTXO” trick. It is a recursive covenant over a commitment-chained single-use seal.
