# Research: a second vocabulary in the Wave-1 compiler engine

**Abstract (Proposal status and scope)** · `abst:w1engine:scope`

This draft proposes, binds nothing, changes no rule and accepts no semantic home. It studies the shared-engine requirement of (`task:guide15-exec:bite-1-2-deliverables`) before stable declarations under (`task:guide15-exec:bite-1-1-deliverables`). Ruling 158 governs (`rule:phase7:wave1-realization-rulings`). The first probe refuted one candidate, not every profile implementation; its result is (`rec:phase7:wave1-profile-probe`) and its code is retained at `refs/evidence/w20b1-profile-probe`, under the subject `test(semantics): probe the keyed profile boundary`. That evidence branches from `0.7.72-dev`; architecture, realization and compiler are byte-identical between that base and `0.7.75-dev`. Reuse named evidence files, never its whole-tree diff against the study base: that diff would remove later keyed birth fragments and campaigns. No implementation or experiment described below has been performed by this study.

**Convention (Source and counting units)** · `conv:w1engine:counts`

Unqualified code citations and counts describe the imported tree at `0.7.75-dev`. Evidence-ref citations explicitly name that ref and do not describe production code. A *seam* below is a named API, data boundary or classifier family, not a count of lines to edit. A *mention* is a whole-word occurrence of a selected type name after omitting lines whose first non-whitespace characters are `//`; imports, declarations and qualified uses count, comments on otherwise retained lines are not removed. These reproducible lexical counts measure coupling, not AST type positions, exhaustive matches, semantic conditionals or a promised patch size. The proposed routes have separately counted migration surfaces; only an implemented diff can supply their final arm and conditional deltas.

## 1. What the engine is typed on · `sec:w1engine:current`

**Fact (The shell is only the first boundary)** · `fact:w1engine:shell`

`OperationRealization` has eleven fields: operation identity, expressions, relations, relation dependencies, two constructibility collections, two lifecycle collections, two disclosure collections and disclosure seeds (`packages/realization/src/operation.rs:13`). Parameterizing only its operation and relation fields leaves the other graph identities concrete. `ScopedRealizationSpec` additionally owns five typed graphs, node maps, schedules, authorization cases and the architecture binding; its operation map is keyed by `OperationId` (`packages/realization/src/derive.rs:70`). Its stable projection has nine fields, including all five graph projections and declassification (`packages/realization/src/derive.rs:289`). The compiler binds that complete owner-validated value, an explicit scope and policy; changing the declaration shell does not change `BoundCompilerInput` or its retained architecture census (`packages/compiler/src/input.rs:115`, `packages/compiler/src/input.rs:171`).

`Relation` has eighteen variants and `RelationEdge` thirteen; `RelationDeclaration` retains a `RelationId` and a set of `ProofAlternativeId` (`packages/realization/src/relation.rs:49`, `packages/realization/src/relation.rs:130`, `packages/realization/src/relation.rs:148`). `RelationId` contains an `OperationId`, `RelationKind` and `RelationSubject`; `ExprId` embeds either `FactId` or that complete relation key; `ProofAlternativeId` embeds the relation key and one of six `ProofKind` variants (`packages/realization/src/identity.rs:283`, `packages/realization/src/identity.rs:359`, `packages/realization/src/identity.rs:386`, `packages/realization/src/identity.rs:406`). The identity closure therefore extends beyond replacing three top-level enum names.

## 2. Candidate engine routes · `sec:w1engine:routes`

**Proposal (A — parameterize the engine vocabulary)** · `proposal:w1engine:generic`

Introduce a sealed vocabulary parameter with associated operation, object, relation, fact, expression, evidence and proof identities; parameterize the bound input, graph weights, requirements, candidate keys, projections and errors through that closure. Each owner supplies validated relation semantics, source/availability rules, proof alternatives, execution cases, discharge and coverage rules. Associated IDs must retain ordering, equality and ownership without using names or numeric positions as policy. A trait containing only `type Relation` would leave the seams in (`tab:w1engine:seams`) unresolved.

Counted proposed footprint: eight stage/binding rows in that table; seven analysis responsibilities required by the guide; eight selected direct type names with 525 mentions in 27 engine/support modules, plus 241 mentions in four consumer modules to audit for specialization. Realization's 23 direct declaration-shell mentions and its five graph payloads also need examination. These are the measured propagation surfaces, not a claim that all mentions change. There would be one generic orchestration implementation and two vocabulary implementations; the number of new trait methods is deliberately unsettled until a minimal complete semantic contract is demonstrated. Unchanged resource counters and graph algorithms need no parameter merely because their module is in the inventory.

This route reuses traversal, closure, enumeration, placement and coverage machinery directly. Its main preservation risks are trait implementations silently changing old classifiers, generic ordering changing candidate identity, loss of typed refusal payloads, and monomorphization hiding two policy engines beneath a common function name. Defaulting every associated type to attestation may reduce consumer edits but cannot prove keyed execution reaches the same algorithms. Source and coverage rules still require a semantic owner; a large collection of arbitrary callbacks would distribute that owner across the compiler.

Ruling-158 reading: generic instantiation alone introduces no runtime profile dispatch. Pure encoding arms and compile-forced relation discharges are separate vocabulary counts. A newly specialized callback that decides policy from keyed-operation identity outside the three entries is a semantic delta even if no `match profile` appears. Acceptance would require zero new such sites and zero growth in the six-site ledger, with the full implementation and callback ledger reviewed; traits are not an exemption.

**Proposal (B — owners produce a shared typed relation interface)** · `proposal:w1engine:interface`

Introduce a validated, target-independent analysis input whose finite records expose semantic identities, prerequisite edges, operand/source rows, constructibility requirements, lifecycle constraints, approved proof alternatives, execution cases, discharge scope/multiplicity and coverage obligations. The attestation owner lowers its existing `Relation` declarations to those records; the keyed owner lowers its independent relation vocabulary. Include an owner-produced per-operation sponsor/funding-region record: family identity, declared flows, decidability and erasure/availability policy. `ORDINARY_LBTC` fixes `ObjectId::PlainLbtc` (`packages/compiler/src/sponsor_region.rs:109`); `GATED_ORDINARY_LBTC_ROLE` assumes every admitted architecture operation sponsors fees (`packages/compiler/src/sponsor_region.rs:153`, `packages/compiler/src/sponsor_region.rs:168`). Neither premise may silently decide keyed funding semantics. Constructors remain private or owner-validated: accepting a caller's asserted `ExternalEvidence` flag would merely allow the caller to disable a covenant clause.

Counted proposed footprint: the same eight stage/binding rows and 27-module/525-mention audit surface as route A, but engine keys and records become shared concrete analysis types rather than carrying a semantic vocabulary parameter everywhere. Two lowerings feed one record domain and one orchestration implementation. Twelve classifier families need disposition: predicate binding, relation operands, proof capabilities/evidence, operand source mapping, authorization/availability, representation/lifecycle extraction, proof-obligation classification, execution-case derivation, discharge classification, carrier/layout eligibility, coverage mutation/projection derivation, and sponsor/funding-region identity and decidability. The twelfth reaches the analysis entry (`packages/compiler/src/relation.rs:150`) through `ordinary_lbtc_role_of` and its gate (`packages/compiler/src/sponsor_region.rs:227`, `packages/compiler/src/sponsor_region.rs:262`). The function ledger below, rather than these family names, bounds semantic adaptation.

Re-derivation must resolve its owner without another selection. Today `revalidate_input` and `derive_expectations` run after binding, and the latter reconstructs `AnalyzedSource` from `input.realization().project()` (`packages/compiler/src/analyzed.rs:365`, `packages/compiler/src/analyzed_validate.rs:334`, `packages/compiler/src/analyzed_validate.rs:398`). Two options are available: re-enter `bind_input` with the retained owner value, placing any selection there; or make the bound input generic over a sealed owner type fixed at binding. Propose the second for the probe: the bound type retains that owner's validated source and statically re-runs its lowering, then the complete validator re-runs the shared stages. The proposed reading is that a type fixed at `bind_input` is that entry's own consequence, not a later semantic selection. No dynamic owner recovery, namespace test or per-case engine-to-owner callback is permitted. This limited owner parameter does not parameterize B's engine keys or replace its finite records with semantic methods; that identity choice is B′ below. The reading requires disposition before the probe, not an exemption inferred after a new dispatch appears.

Discharge, source and case records are finite tables indexed by sponsor case, object-keyed representation selection and derived amount visibility, with source rows additionally keyed by approved proof alternative. They are not per-relation constants. A selected proof plan selects rows; mixed conservation retains its typed refusal (`packages/compiler/src/case.rs:124`). CompactAsh has four case keys: two sponsor states times Explicit/PublicCommitted; TransferLive has four: two sponsor states times Explicit/PrivateCommitted (`packages/compiler/src/tests/case_tests.rs:47`, `packages/compiler/src/tests/case_tests.rs:70`). Thus there are four case rows per relation per pilot, eight operation-case keys in the combined scope, not a cross-operation product; source-table size is bounded by four times the sum of approved-alternative operand counts per pilot. CompactAsh conservation stays readable in all four cases; TransferLive has two readable and two committed cases, the latter discharged by evidence (`packages/compiler/src/placement.rs:529`). Precompute finite owner tables from admitted declarations and validate their complete census. Needing a case-dependent callback into the owner overturns this form of B.

This is a larger semantic extraction than wrapping the existing enum in a sum. The shared interpreter must retain typed evidence, availability and boundary semantics, not accept string predicates or opaque closures. Some existing primitives can survive unchanged; rooted attestation policies, representation-specific conservation and sponsor rules must be derived by their owner or expressed by explicit finite vocabulary. Reuse covers all seven guide responsibilities, including genuine empty lifecycle/representation sets where keyed declarations impose no such constraints. No empty set is a substitute for a missing obligation: validate it against the original declaration.

Preservation risks are information loss in lowering, a weaker trusted-input boundary, old coverage subjects being coalesced, or a shared enum quietly becoming attestation plus keyed special cases. Keep the old attestation projections available byte-for-byte; an additional internal analysis projection is not a schema-version change. Audit the four specialized consumers and all directly affected downstream consumers, even when an attestation compatibility view leaves their source unchanged. The measured counts do not promise a smaller patch than A; the benefit is an explicit, inspectable semantic contract and one algorithmic input domain.

Ruling-158 reading: selection belongs at the named owner entries; their helper lowerings may translate relation variants but may not hide a new operation-selected engine. The shared algorithms consume facts about relations and never ask which contract they came from. New interface variants and their compile-forced discharge arms are relation vocabulary and must be listed, including cases added to carrier and coverage interpretations. Namespace encoding arms are identifier vocabulary. Any new semantic dispatch on profile/keyed-operation identity elsewhere, including inside a lowering helper, refutes this candidate under the unchanged rule. Existing baseline sites that move must be mapped as moves, not silently subtracted to cancel a new site.

**Proposal (B′ — finite records with identity parameters)** · `proposal:w1engine:identity-hybrid`

Combine B's finite owner-produced records with an engine parameterized only over ordered identity types, with no policy methods on those keys. Keep B's statically bound owner for re-derivation. This carries A's propagation cost through keys, projections and typed `CompileError` payloads: the same 525-mention engine/support and 241-mention consumer audit surfaces, the same 49-function adaptation ledger, and two monomorphized instantiations of one algorithmic engine. It avoids A's per-stage semantic callbacks. Derived `Debug` does not print generic type parameters, so an attestation instantiation retaining the existing fields, variant names and payload types can preserve projection bytes without B's mapped compatibility views; this is a preservation opportunity to test, not a guaranteed result. Refusal payloads also retain owner-specific key types.

B′ risks generic propagation, compile cost and accidental constraints on key types; B risks a compatibility view for every old identity-bearing projection type (`packages/compiler/src/analyzed.rs:183`). B does not demonstrably dominate B′. Keep B as the first experiment because its common concrete record domain is easier to inspect, but make B′ the first fallback if B stops, before A with semantic callbacks. Its natural home has B's two-owner interface and A's independent identity implementation options. Its counted-delta rule is identical: two monomorphizations are not two semantic engines, but any later owner selection or keyed-identity policy arm refutes the candidate, and cross-profile leakage reopens the home.

**Proposal (C — a separate keyed realization with its own small analysis)** · `proposal:w1engine:separate-analysis`

Put keyed declarations, validation and their dedicated analysis in a separate crate. The narrow argument is that SOURCE has only evidence obligations, MERGE only two per-member predicates plus evidence, and neither needs attestation's amount-representation search, sponsor cases or lifecycle exits. A direct finite analysis can consequently be easier to inspect than adapting every attestation classifier. The evidence ref demonstrates the scale of the vocabulary, not proof that the seven responsibilities can be omitted (`rec:phase7:wave1-profile-probe`).

Counted proposed footprint: one new owner crate, two declarations, one dedicated analysis entry; zero required modifications to the 27 existing engine/support modules or four target consumers if the new API is entirely separate. Binding and downstream keyed consumers remain new work. The inherited probe has five relation variants, twelve vocabulary arms and four identifier arms; these are a starting witness count, not a forecast for a production crate. Source, constructibility, lifecycle, proof, placement and coverage would each need either a justified trivial result or new implementations and validators: seven responsibility dispositions, not seven reused stages. Reusing Petgraph, containers or a search counter does not meet the guide's engine-reuse requirement.

This route has the lowest direct first-contract code risk but the highest risk of divergence between two correctness engines and of vacuous coverage. A public separate API could have zero new dispatch inside the old engine, whereas a common `analyze_profile` wrapper would repeat the witness's one forbidden site. Zero there does not satisfy (`task:guide15-exec:bite-1-2-deliverables`): C requires an explicit amendment or exception to reuse, supported by evidence that adapting the shared engine costs more than maintaining the independent semantics. This draft cannot grant that exception. Moving the same bypass into another crate does not cure the witness.

## 4. Recommendation and second probe · `sec:w1engine:probe`

**Proposal (Prefer a typed interface, subject to evidence)** · `proposal:w1engine:recommendation`

Prefer B for the next experiment. The algorithms already operate on finite ordered graphs, alternatives, cases and obligations, while the policy-bearing classifiers have identifiable inputs and outputs. Making those outputs a complete typed owner contract is more inspectable than distributing semantic callbacks through generic algorithms. It also makes the profile/separate-crate comparison honest: either owner must furnish the same validated input. This is an engineering preference, not evidence that B has the smallest diff or that the profile stands.

Overturn it at a lost projection or refusal boundary, an unrepresentable obligation (including case-dependent lowering needing an engine-to-owner callback), re-derivation needing an owner selection after binding, an attestation constant or law leaking into keyed analysis, or a duplicated engine stage. Only after a B stop, compare B′ and then, if necessary, A on the same seven-stage subjects. Fix the comparison thresholds before those runs: changed files, types, ledger functions, semantic sites and compatibility-view size, alongside compile time, public API breadth and typed refusal quality. Do not claim an unperformed A comparison or use an undefined "materially smaller" threshold. Prefer C only after a governing reuse exception supported by that comparison; absence of keyed amount/lifecycle choices alone is not such evidence.

## 5. Ambiguities and open questions · `sec:w1engine:questions`

The five proposed answers below were adopted as rulings 166 to 170 at (`rule:phase7:wave1-engine-rulings`), which now govern.

**Question (Interface authority and location)** · `q:w1engine:authority`

Proposed answer: keep record types crate-private in compiler and both lowering modules reached through `bind_input`, with the fixed owner type carrying statically bound re-derivation as described in B. Each lowering reads only its owner-validated declarations; compiler file location does not transfer semantic ownership. The dependency direction remains architecture → realization → compiler. For production, put record types below both producers: realization if both declarations stay there, or an interface package when a separate keyed crate becomes a real second producer. A trait in compiler implemented by realization would create a cycle. Preserve today's independent validation depth: `derive_expectations` re-runs every stage and rebuilds the source (`packages/compiler/src/analyzed_validate.rs:334`, `packages/compiler/src/analyzed_validate.rs:398`); re-run lowering from retained source, never trust a digest or flag. This proposed answer authorizes no new package and awaits disposition.

**Question (Meaning of reuse with empty stages)** · `q:w1engine:reuse`

Proposed answer: yes, under three conditions. The keyed input reaches the shared stage through one orchestration call and its typed empty output appears in the projection; the keyed lowering derives that emptiness from the declaration census and the complete validator re-checks it; a keyed negative adding a representation/lifecycle-exit record is refused by owner census or shared `MissingRepresentationChoice`/`MissingLifecyclePath`. Retain nonempty attestation controls too. These are negative subjects, not invented keyed laws. SOURCE's proof planning, placement and coverage must process all four evidence obligations as external-evidence discharges and retain them in coverage, using `CarrierRole::ExternalEvidence` where a role is needed (`packages/compiler/src/carrier.rs:62`). Its runtime assignment list can be empty, because evidence has no runtime eligibility; that is a valid shared placement result, not an empty successful result bypassing the stage (`packages/compiler/src/carrier.rs:395`, `packages/compiler/src/placement.rs:1084`). A bypass or handwritten keyed result is not reuse. The home disposition must confirm this proposed reading.

**Question (Boundary of relation vocabulary)** · `q:w1engine:vocabulary`

Proposed answer: classify a site by what it reads. A result depending only on interface variants and their fields is relation vocabulary; list and count it. A policy decision reading owner, namespace or operation identity is semantic dispatch, whether direct, through an attestation constant such as `ORDINARY_LBTC`, or through a dynamically selected owner trait after binding. A type fixed once at `bind_input` is proposed to be that entry's own consequence; statically re-running that fixed owner's lowering introduces no selection. Lowering helpers do not grant permission for hidden keyed-identity policy. If the design must recover an owner after binding, seek a ruling before implementation. Keep the three entries and report baseline moves without canceling new branches; cross-profile leakage remains an independent failure condition.

**Question (Base artifacts and comparison scope)** · `q:w1engine:artifacts`

Proposed answer: use tag `0.7.75-dev`, whose engine crates are byte-identical to the evidence base `0.7.72-dev`. Commit the capture on a branch from that tag and transport it by the sanctioned git route. Record each row's realization scope, compiler scope, constructor, limits and actual projection or typed refusal as specified in (`tab:w1engine:capture`); use derived `{:#?}` with the recorded toolchain, blob IDs and measured file sizes. Retain separate publication evidence. The ten result files are not ten promised successful projections. A later base requires a fresh census and provenance. No host build or capture is implied here; an unnamed transport is a preflight blocker, and log tails are never artifacts.

**Question (Cost and fallback)** · `q:w1engine:cost`

Proposed answer: stop B at the first lost projection/refusal boundary, unrepresentable obligation (including a case-dependent engine-to-owner callback), owner selection after binding, attestation constant/law reaching a keyed path, or duplicated stage. Then try B′ on the same seven-stage subjects before A with semantic callbacks. Before fallback runs, fix thresholds for changed files, types, ledger functions, semantic sites and compatibility-view size; also compare compile time, API breadth and typed refusal payloads. The initial B probe does not pretend to measure A. Only amended guide text or a new governing Phase-7 ruling, resting on the recorded comparison, can relax bite 1.2's reuse requirement for C. These are proposed answers, not dispositions or authorization of a production refit.
