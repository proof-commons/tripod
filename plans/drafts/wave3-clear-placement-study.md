## Reading and consumer census · `sec:clear-placement:consumers`

The set answers which complete carrier assignments satisfy a fixed proof candidate and operation. A member assigns every active runtime relation-case, with a canonical carrier list per key and exactly the union of its selected carriers' layout dependencies. It is not a selection of a preferred implementation, a transaction layout, an execution verdict or a count of transactions. engine_operation.rs already separates operations; the expensive product is inside one operation. engine_program.rs selects proofs and cases before calling it. The following census follows both direct field readers and their public projections; test-only compatibility paths are distinguished from production.

In particular, target.rs deliberately hides analyzed members and counts; this design adds no public product API.

## Product and cross-factor conditions · `sec:clear-placement:product`

The measured 139,999 retained out of 140,000 visits is not evidence of a rejected combination. In engine_placement.rs:visit, complete_assignments is incremented before construction, validate_placement, the candidate-cap check and candidates.push. Validation uses `?`: any invalid member aborts the entire enumeration; it does not filter it. Deduplication and final feasible_placements happen only after recursive search succeeds. An in-flight sample can therefore lag by one. The diagnostic run did not complete, so its sampled retained count is not the final cardinality.

| Condition spanning rows | Owner and relation | Factor formulation |
|---|---|---|
| Exact runtime key census and no duplicated assignment key | validate_census/validate_placement compare plans, eligibility and assignments | Check factor keys once against independently derived runtime keys; one selection per key. |
| Layout equality | validate_assignment requires each selected entry's layout in stated layout; validate_placement refuses duplicates and any stated layout unused by all selected entries | Member layout is the canonical union of selected local layouts. Shared requirements are deduplicated, not incompatible. Check that exact union for an offered member. |
| Operation locality and no cross-operation relation/coverage dependency | analyzed_operation.rs factorization/locality; engine_operation.rs prerequisite/coverage graph assembly | Check all local options and independent graph edges once. They constrain the operation decomposition, not combinations of carriers inside an admitted operation. |
| Coverage join, sponsor opacity and operation layout inclusion | engine_coverage_join.rs, analyzed_validate.rs, analyzed_operation.rs | Every option's carrier/layout alternative must join and stay inside the operation census; inspect each local option. No selected-carrier capacity or co-location constraint. |

Scope, multiplicity, quantification, source availability, unconditional/optional-carrier exclusion and duplicate carriers are local to one relation-case. Proof compatibility and shared bounds are upstream; they must not be turned into placement-factor independence assumptions. Graph prerequisites order obligations, not their selected carriers. There is no carrier exclusivity, shared target resource, common coordinator choice across relations, or condition coupling sponsor-case assignments in this placement language. A future such constraint must reopen this representation, not be ignored.

The pure-product claim is qualified: canonical bound lowering must supply coherent options. Eligibility has separate entries (validation) and options (generation); engine_attestation/placement.rs even reads the first versus last duplicate plan for them. Arbitrary malformed records can have differing option layouts, which a different selected row's union can mask. Thus do not claim factor-local checks equivalent for every hand-built Records value. The new product constructor checks exact runtime census, unique factor keys, nonempty canonical options, each option's carriers/quantification against validation entries and exact local layout equality to those entries. Refuse incoherence rather than silently pruning it. The legacy enumerator and its malformed-input error order stay unchanged. Canonical owner lowering must be proved to meet this precondition in the selected equivalence tests.

For admitted factors, an option fixes one canonical assignment and its local layout. Choosing one option per key yields distinct assignment maps; the layout is a function of that map. Deduplicate identical options before counting, retaining distinct carrier identities even when layouts coincide. Zero runtime factors denote one empty assignment with empty placement-local layout; an empty option set is a typed no-eligible-carrier refusal, not a successful empty analysis. These facts give the product argument without a general constraint solver.

## Recount of Clear factors · `tab:clear-placement:factors`

Read from packages/realization/src/declarations/clear.rs:families/relations, placement.rs:classify_discharge/family_activation, carrier.rs:candidate_carriers/coordinator_anchors/quantification, engine_attestation/placement.rs:admissible_carriers and engine_placement.rs:options. A fixed representation/proof candidate has two sponsor cases. STATE and ASH are mandatory inputs, PlainLbtc is optional. Let G be the two OperationGlobal roles anchored in STATE and ASH, F(x) the InputFamilyCoordinator for x, and M(x) EveryInputFamilyMember for x. Input recognition alternatives carry PerMember for M and CompleteFamilyProof for G/F; all other listed alternatives carry Single. A coordinator anchored in STATE is not the same typed carrier as F(STATE), even with exactly one STATE input. This is a static code recount, not a rerun of the timed worker probe.

The product is 3^5 × 4^5 × 2^46 = 17,509,995,351,216,488,448, below u64::MAX for this candidate but much larger than the 100,000 materialization cap. Forty-four declared relations yield 88 relation-case rows for the selected representation; 56 have runtime factors and 32 do not. The preselection 352 rows correspond to four representation pairs times two sponsor cases times 44. Report anchors, structural DataOutputs, representation, permissionless authorization, constructibility, substrate evidence and lifecycle obligations must remain in bundles although they add no runtime factor.

All 56 factors are choices under the present compiler contract. The two sponsor cases repeat some options but have different keys and conditional source/layout obligations; equating their selections is an additional restriction, not dead-code removal. Cardinality bounds constrain transactions, not how many compiler carrier assignments exist. Exactly-one STATE does not make recognition compiler-static. Five copy assignments still require input/output equality. The G/F distinctions could conceivably be quotiented by a future target equivalence, but no such equivalence exists in this abstract planner, whose coverage records distinguish those carriers. The 3.2c lowering therefore does not have a smaller correct replacement evident in this tree. Reducing these choices would require a separate semantic ruling, not a performance repair.

## Selected contract and compatibility · `sec:clear-placement:contract`

Select a finite exact product owned by engine_placement.rs, with private canonical construction, immutable keyed local options and local layout dependencies. It supports factor inspection, exact factor equality after fresh lowering, validation of one offered complete member (including exact layout union), and explicitly bounded materialization. It has no implicit IntoIterator, indexing, unbounded collect or fallback that enumerates when a validator asks for equality. No SAT/BDD/general constraint representation is justified by the census.

An exact numeric count is not a production consumer requirement. Retain factor cardinalities as the exact symbolic count; a diagnostic checked u128 product may return overflow, never saturation represented as an exact answer. Existing enumerated len/count and search reports keep their meanings. Product construction records actual factor/option visits and zero complete assignments/materialized candidates, with separate structured factor_count/option_count and optional cardinality diagnostics; it must not report the mathematical product as work performed. Use existing state-limit refusal to bound factor construction (one admission for the root, each factor and each option); account separately from legacy DFS states. The public maximum_candidates remains a bound on materialized candidates, not an implicit maximum represented cardinality. For Clear this deliberately changes the former internal candidate-cap refusal into a complete product result. Existing operation routes, cap refusal boundaries, ordering and reports remain unchanged. Explicit materialization still returns the existing typed candidate/state limit error and no partial value. Do not remove, raise, or reinterpret the cap as a factor-option limit.

Compatibility has two adapters, not two planners. Keep the legacy enumerate entry and Vec storage for keyed and all currently active attestation operations. Generalize only shared result containers Operation, Plan and Program with a placement-storage type parameter defaulting to their present Vec candidate type; keep existing analyze/analyze_prepared signatures and record literals unchanged. The common assembly body takes a private fixed storage strategy; a product-enabled attestation entry uses the same proof/case/coverage/lifecycle stages. The attestation owner requests product storage for Clear, including its partners' mixed scopes; the engine receives storage policy explicitly and never interprets operation identities to choose semantics. Records, Case/Tables, Facts and proof Records gain no fields, and frozen keyed error adapters gain no new engine Error arms. Local product defects use existing placement errors; product projection mismatches may add a compiler-owned error in error.rs with a relation-case coordinate.

The internal AnalyzedOperation.feasible_placements becomes a closed enumerated-or-product value; all direct readers in the census dispatch explicitly. Enumerated Debug delegates directly to the old BTreeSet formatter (including alternate formatting), with no variant wrapper, so the old AnalyzedOperation field name and projection bytes survive. The Clear product has its own explicit Debug form. This is an internal type change, not a field addition to a pinned literal-built record or a public placement API. No clever Deref/iterator compatibility that might enumerate a product is allowed. Existing test literals/accessors may need explicit conversion or an enumerated accessor; a refusal is preferable to accidentally expanding Clear. The selected equivalence control must compare complete old/new stable projections and public facades, not merely cardinalities.

An operation's coverage alternatives are the union of all validated local assignment options, passed into the existing engine_coverage_join::alternatives. Operation-wide layout remains derived from case facts and checked against all option layouts. Fresh validation re-enters from bound source and compares canonical factor keys, carriers, quantifications and layouts exactly; it does not trust offered coverage, factor counts or its own constructor output as the expectation. Membership validates one choice per runtime key plus the exact selected layout union, not merely per-carrier eligibility. A factor's presence in eligibility alone does not establish completeness of the offered product.

Bounded product materialization first compares the factor cardinalities with maximum_candidates using checked multiplication (overflow also exceeds the u64 cap), refusing CandidateLimit before any huge expansion. This is the new product accessor's behaviour; preserve legacy DFS limit ordering. The Clear cap-control therefore does not spend 100,000-member wall time. Product-mode tracing explicitly identifies storage mode, factor/option work and zero materialized members; do not present a zero legacy feasible_placements work counter as an empty semantic set. Execution reports remain outside stable semantic equality.

## Costs, rulings and rejected alternatives · `sec:clear-placement:decisions`

For one measured-shape Clear candidate the placement work becomes 56 factor keys and 127 options, rather than about 17.5 quintillion members. Across four candidates that is 224 factors and 508 options per derivation; independent re-derivation repeats bounded local work. Storage is proportional to local carrier/layout bytes. With ordered maps/sets, factor normalization and joins scale with those bytes and logarithmic lookup, plus existing proof/case/coverage graph costs; no product cardinality term remains. Avoid per-option rescans of complete placements. Four proof candidates/40 states and 66.2 ms preparation/1.44 ms proof search are the supplied probe's observations, not independently timed results here. The expected warm complete Clear analysis plus fresh validation is 1–10 seconds; a conservative focused control budget is 120 seconds after build, suite 2–8 minutes and the inherited ten-minute diagnostic ceiling. These are estimates, not acceptance evidence: 3.2e records actual phase walls, factors, options, re-derivations and peak memory, and revises the estimate if exceeded rather than declaring success from structural complexity alone. Full import gates retain the observed 950–4,265-second range; two added gates cost 1,900–8,530 seconds beyond the original schedule.

No new invariant is minted. The stored-y_l/derived-Y distinction remains (`inv:guide15-exec:clear-census`); the underlying STATE succession/accounting laws remain (`[RZ-inv:invariant:succession]`) and (`[RZ-inv:invariant:accounting]`), with no attempted new proof of them. Exact placement preservation and non-partial refusal already belong to the compiler planning contract (plans/guides/guide_seven.md sections 9, 13.8 and 20.4). The proposal changes representation and the Clear enumeration boundary, not these semantic obligations. If independence is to be a permanent system invariant, request a separate ruling with statement: “For canonical lowered placement records of a fixed proof candidate and operation, the admitted complete assignments are exactly the product of nonempty local alternatives with layout determined by union; any new cross-factor constraint reopens that contract.” Argument: current validators have the factor/union form above; resource/co-location constraints would invalidate it. Recommendation: adopt a scoped compiler representation precondition and reopening rule now, not a system-wide inv; the estate's invariants-precede-assertions rule is not permission for this study to mint one.

Questions for adoption are (`rule:phase7:clear-placement`): approve the product contract and retain all lowering choices; approve the additive storage adapters with legacy keyed/default paths and Clear-only product selection; approve candidate-limit semantics and truthful work counters; approve the two prerequisite packets and independent review at the shared-engine integration boundary. Recommendations are affirmative because the census contains real indexed and byte-sensitive consumers but no consumer requiring Clear's full enumeration. These are proposed compiler-plan changes, not adopted rulings. No change outside compiler planning is selected; if implementation discovers one is necessary, return that specific contract/freeze conflict before editing it.

| Rejected alternative | Reason |
|---|---|
| Raise the candidate cap or run longer | The product is many orders of magnitude beyond ordinary time/memory; a larger prefix is still no complete plan. |
| Keep only the first, cheapest or canonical coordinator | Drops admitted choices and coverage alternatives without a supporting semantic rule. |
| Merge sponsor cases, collapse singleton recognition or omit copy assignments | Confuses transaction semantics with carrier selection and erases independently keyed obligations. |
| Couple all global relations to one coordinator | Invents a cross-factor restriction absent from the present compiler contract. |
| Validate only the local facade while complete analysis still fails | Breaks the complete validated-plan precondition and leaves mixed-scope analysis unresolved. |
| General SAT/BDD/lazy enumerable set | No current consumer needs arbitrary constraints; lazy traversal still makes equality/count/collect exponential and obscures caps. |
| Replace every operation's public/retained representation at once | Needlessly changes indexed keyed consumers and risks frozen sources/capture bytes; preserve their bounded enumeration. |
| Add a Clear-only second planner | Duplicates shared placement/coverage ownership; storage policy belongs in adapters over the existing engine. |

This study's tables are design evidence. The record of completed implementation, exact gate walls and preserved bytes belongs in plans/history/wave3-compiler-records.md only after those checks run.
