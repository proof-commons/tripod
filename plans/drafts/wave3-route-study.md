# Research: routes for Wave 3 compiler operation plans

**Abstract (Proposal status)** · `abst:w3route:scope`

This study proposes execution Wave 3 at `0.7.191-dev`, with concept Wave 2 as its semantic reference. The [completion strategy](wave3-completion-strategy.md) supplies exact packets. Rulings 221–234 are proposals; 220 is reserved by another landing. No code, governing contract, plan proof or native result is adopted here (`rule:drafts:authority`).

**Convention (Evidence and proposed names)** · `conv:w3route:sources`

Paths and labels identify inspected evidence. Proposed types, tests and files describe future work. The semantic owners remain authoritative; each changed interface requires the eight-item ledger at (`rule:guide15:consume-pipeline`). New tests are named for their claim, without a schedule prefix.

## 1. Routes and ordering · `sec:w3route:routes`

The eight deliverables are Burn, revalidated compact ASH, Clear, a Phase-7 scope, relation/carrier/layout/coverage/lifecycle censuses, ASH constructor closure, validators and independent oracles. “All three validated plans reconcile relation/carrier/layout/coverage/lifecycle censuses, reject focused corruptions, and agree with independent small-instance oracles.” (`gate:guide15-exec:wave3-gate`). Inherited declarations, Wave-0 closure/region evidence and Wave-1 placement supply inputs rather than the new proofs (`assum:guide15-exec:wave3-inherited-inputs`).

| Alternative | Cost and reopened boundary | Selection |
|---|---|---|
| Sibling facades on existing attestation lowering/shared engine | New operation meanings, source/placement/evidence tables and fresh validators; pilot compatibility and mixed scopes reviewed | Select; existing owners already contain the algorithms (`packages/compiler/src/engine_attestation/program.rs`) |
| Parallel Burn/Clear planner | Duplicates source, proof, carrier, layout and coverage algorithms and their validation | Reject; no ownership fact justifies it (`rule:guide15:consume-pipeline`) |
| Universal facade/keyed migration | Reopens downstream APIs and both source freezes without an operation requirement | Reject; preserve existing facade names and add siblings (`packages/compiler/src/lib.rs`) |
| All new laws external-report-owned | Avoids lowering work but loses required runtime/coordinator obligations | Reject; report evidence cannot stand in for emission (`rule:guide15:carrier-placement`) |
| Public activation before complete tables/oracle | Smaller patches, but exposes incomplete plans through silent selectors | Reject; staged per-operation lowering and private facade tests precede activation |
| Burn then Clear | Burn supplies simpler data-output/binding experience; Clear adds STATE/clamp/residual | Select, without borrowing Burn's expected data or proof |
| Clear then Burn | Exercises STATE early but starts with the larger facade/law census | Reject for review cost; no dependency demands it |
| One late oracle bite | Defers discovery of missing plan obligations | Reject; each activation includes its own independent oracle |
| Explicit-only Burn as final wave output | Saves mixed-selection work but drops accepted private change | Reject under ruling 141, disposition 3 and the realization/Wave-4 contracts (`proposal:w3route:representation`) |

Sequence: adoption → lifecycle and shared-bound guard → vocabulary → side-qualified keys/cases → dormant Burn lowering → compact revalidation → Burn facade/validator → Burn oracle/explicit activation → dormant Clear lowering → Clear facade/validator → Clear oracle/activation → three remaining private-change packets → scope facade/closure → scope oracle → candidate reopenings → closing gate. The early compact packet revalidates changed shared owners before the first activation. The early side-key packet preserves the engine-base capture before dormant lowering; later mixed-selection changes also rerun the compact baseline. Nineteen packets and their costs are specified at (`sec:wave3:execution`).

## 2. Twelve design questions · `sec:w3route:questions`

### Q1. Choices, availability and the private exit · `proposal:w3route:lifecycle`

Burn declares input/output SideRepresentation for ReceiptLive but only an object-level Representation for Ash; it nevertheless requires three ReceiptLive exits. Existing lowering makes choices only from Representation, and the engine checks required choices against objects from every operation. Burn alone therefore lacks its own ReceiptLive choice, while TransferLive can silently supply it (`packages/realization/src/declarations/burn.rs:303–345`), (`packages/realization/src/burn_clear_laws.rs:155–166`), (`packages/compiler/src/engine_attestation/lifecycle.rs:40–58`), (`packages/compiler/src/engine_lifecycle.rs:155–166`).

Establish operation-local required-choice membership at the lifecycle/engine level, with Burn-owned synthetic records and an omission that refuses even with TransferLive in scope. Complete Burn analysis is not reachable until dormant lowering removes the stage guards. After the side-key packet, lower Burn's input SideRepresentation directly into a Burn-owned input-qualified ReceiptLive choice {Explicit}; the output choice is independent and cannot supply it. The object-level union feeds lifecycle only. This is a compiler subject, distinct from realization's per-declaration closure pin (`plans/packages/realization.md:409`).

Qualify scope/path availability with the exit operation's own input admission, not a target-plan filter or existence of an emitted proof. Add an owner-supplied eligibility table to the existing lifecycle records and `DeclaredInCompilerScopeUnavailable` to the status. Scope absent → outside; scope present plus admitted input mode and required path → available; scope present but inadmissible mode → unavailable and outstanding. Preserve the graph and every non-available row. Eligibility means compiler input admission only, not target implementation or deployed closure (`rec:backlog:wave2-wave3-receiver`).

| Exit operation | Object | Literal input-admitted modes |
|---|---|---|
| CompactAsh | Ash | Explicit, PublicCommitted |
| TransferLive | ReceiptLive | Explicit, PrivateCommitted |
| AnnounceMaturity | State | Explicit, PublicCommitted |
| Burn | ReceiptLive | Explicit |
| Clear | Ash and State | Explicit, PublicCommitted for each |

The table comes from the five declarations under `packages/realization/src/declarations/`. Target explicit-only ASH selection must not narrow this semantic table. The private receipt-to-Burn edge remains required but unavailable even after private output change is planned.

The shared proof engine filters lifecycle rows to selected (object, mode) pairs (`packages/compiler/src/engine_proof.rs:279–289`). An explicit Burn plan cannot publish the private receipt row. The actual public reaching subject is TransferLive+Burn compiler scope: live-transfer Explicit implements Burn; its PrivateCommitted projection lists Burn outstanding with the new status. Phase-7 additionally publishes all declared-representation obligations absent from every selected facade, derived from the full lifecycle analysis. Thus the private route cannot vanish from the public scope by omission. At the early lifecycle bite, synthetic engine/analyzed rows and a status-corruption comparison establish propagation; public survival waits for activation. `validate_compact_lifecycle_projection` checks graph paths, not status (`packages/compiler/src/lifecycle.rs:88–106`).

A relation owns only the lifecycle rows of its own operation's selected mode for that object — the output-side choice where the object is side-qualified; plan-level completeness may keep the candidate union. Change engine_requirement::owned_lifecycle and both attestation call paths to pass the owning operation and selected qualified choices, rather than filtering only (object, exit). Candidate filtering alone retains modes chosen by any operation and cannot establish this ownership (`packages/compiler/src/engine_proof.rs:279–289`), (`packages/compiler/src/engine_requirement.rs:32–47`), (`packages/compiler/src/engine_attestation/requirement.rs:115,472–482`).

| Qualification alternative | Cost / limitation | Choice |
|---|---|---|
| Shared traversal consumes owner eligibility | Changes records and existing filters; empty keyed records need only the default initializer; status is consistent before proof filtering | Select, together with operation-local choice validation |
| Owner-side downgrade in compatibility_view | Leaves traversal unchanged, but shared proof/program joins first see scope-only statuses unless every restore/join boundary is also revised | Reject: duplicates qualification timing and risks contradictory projections (`packages/compiler/src/engine_attestation/lifecycle.rs:158–167`) |
| Burn facade-only flag | Cheap but cannot expose the row filtered out before that facade, and leaves old completeness callers unsound | Reject |

### Q2. Object sets and multi-object representation evidence · `proposal:w3route:objects`

The present provisional object sets are not themselves a complete representation dependency model. `single_representation` returns None when more than one named object has a selection; None means “no single selection,” not absence of representation-dependent sources (`packages/compiler/src/engine_requirement.rs:9–31`), (`packages/compiler/src/engine_attestation/requirement.rs:100–118,391–436`).

Select Burn DataOutputs → {}: its body relies on bound schema/count/tag/association and returns true. Select Clear DataOutputs → {State, Ash}, because its destruction quantity is compared to the derived clamp. Retain and independently test ClearClamp→DataOutputs regardless of that set. The alternative {} for Clear is tenable only with complete dependency/source evidence; the two-object set is clearer and retains that evidence explicitly (`packages/realization/src/burn_clear_laws.rs:303–313,554–558`), (`packages/architecture/src/spec.rs:1434–1441,1581–1588`).

Other proposed sets: SideRepresentation → named object; BurnBinding → {ReceiptLive,Ash}; ClearAssignment/ClearFloor → {State}; ClearClamp/ClearFlow/ClearBinding/ClearCanonicalDeltaPolicy → {State,Ash}. Accept None on the two-object relation summary, while exact per-operand `WhenRepresentation` activations, source rows, selected case coordinates and dependency joins carry all representation dependence. Validators compare those collections, not only the optional summary. The side-qualified private-change extension adds side activations rather than collapsing two modes to that optional summary. Pin literal object/source/activation tables before each operation activates; no empty fallback.

### Q3. Mixed scopes, shared reasons and one bound source · `proposal:w3route:scope`

Choose scope-derived exit sets for every facade and one bound input for the Phase-7 scope, conditional on operation-local lifecycle-row ownership from Q1. Without it, another operation's selected mode contaminates the projection: compact/announcement become ambiguous, and live private Burn is both implemented and outstanding. Joining three standalone plans cannot establish cross-operation lifecycle closure. Shared-bound reasons and exact partner-exit status changes are the only allowed differences in the named singleton/mixed comparisons; remaining operation-owned projections must agree (`plans/backlog.md:762`).

Live transfer currently requires implemented {TransferLive} and outstanding {Redeem,Burn} and requires equal lifecycle closures across its two representations. Announcement similarly hard-codes Clear among five outstanding exits and also requires equal closures across its modes; that equality is harmless for AnnounceMaturity+Clear because Clear admits both STATE modes. Both refuse the proposed mixed scopes today; the equality restriction is an additional live-transfer obstacle because Explicit and PrivateCommitted diverge when Burn is in scope (`packages/compiler/src/live_transfer_plan.rs:1798–1821`), (`packages/compiler/src/maturity_announcement_plan.rs:1183–1204`).

| Scope extension | Expected scoped result / test change |
|---|---|
| TransferLive + Burn | Explicit: implemented {TransferLive,Burn}, outstanding {Redeem}; PrivateCommitted: implemented {TransferLive}, outstanding {Redeem,Burn}, with Burn unavailable. Common facade summary uses implemented intersection and outstanding union; per-representation projections remain authoritative. Update `the_lifecycle_closure_implements_transfer_and_leaves_burn_and_redeem_outstanding`, `an_altered_lifecycle_exit_is_rejected`, and representation-equivalence checks in live_transfer_plan_tests.rs |
| AnnounceMaturity + Clear | Both admitted STATE modes: implemented {AnnounceMaturity,Clear}; outstanding {AdmitDeposits,Cycle,Redeem,ReceiptRelabel}, count 5→4 for this wider scope. Update maturity_announcement_plan_tests.rs:484–488 and the lifecycle corruption/equivalence checks |
| CompactAsh + Clear | Selected explicit Ash: implemented {CompactAsh,Clear}, outstanding empty, scoped release_complete true. Update `the_plan_implements_compact_ash_and_leaves_clear_outstanding` in operation_plan_tests.rs:472 and its offered-plan lifecycle corruptions |
| Burn + CompactAsh + Clear | All three facades consume the same bound scope; declared but unselected representation obligations are published separately, including private receipt→Burn unavailable and exits not in scope |

These changes affect lifecycle sets, status rows, scoped completeness and representation-equivalence normalizations; they do not change the standalone relation/case/placement/layout/coverage/carrier figures. Existing standalone tests keep their old expectations and gain mixed-scope rows. No candidate bytes are generated here and neither pin inventory contains these facade/test paths; source/candidate compatibility still gets the full gate. Do not interpret scoped release_complete as linked deployment completeness. No Wave-3 packet emits from a mixed scope: tapscript's bundle refuses the release-complete compact plan with PlanClaimsReleaseComplete (`packages/tapscript/src/bundle.rs:1804–1811`). Closure summary types keep their shape; existing readers at packages/linker/src/state_bundle.rs:657, live_bundle.rs:846 and packages/vectors/src/live_report.rs:6690–6692, live_minimality_report.rs:1577–1579 retain standalone pins, including live 1 implemented / 2 outstanding.

Transfer/Burn controls land with Burn activation; compact/Clear and announcement/Clear controls land with Clear activation, satisfying “before activation” in the receiver. The final scope bite adds the full three-operation comparison, not the first mixed controls. Separate realization tests ensure a missing row in one declaration cannot be repaired by company.

Select a narrow shared-bound guard before activation: equal-visibility union stays, but a multiply-declared bound with an incoming edge or explicit seed refuses. The existing declassification merge owns it; no new propagation algorithm. Proposed `UnsupportedSharedBoundDependency` carries bound, declaring operation and IncomingEdge/Seed kind. This deliberately tightens the admission boundary of (`gate:backlog:wave2-bite-2-7a`) prospectively; adoption states why and preserves prior evidence. Its acceptance is only seed-free/one-edge/one-seed controls; mixed scopes and local omission belong to the separate scope ruling (`plans/backlog.md:740–741`).

### Q4. Normalized input and private change within this wave · `proposal:w3route:representation`

Explicit-only is an intermediate milestone, not the final Burn deliverable. Ruling 141 accepts “normalized-first with private change”; disposition 3 preserves that boundary; realization assigns the mixed-conservation route to Wave 3 plans and Wave 4 target assessment; the Wave-4 gate includes confidential change outputs and proofs (`plans/phases/07-burn-and-clear.md:205`), (`rule:guide15-exec:disposition-3`), (`plans/packages/realization.md:438`), (`gate:guide15-exec:wave4-gate`). No accepted obligation is narrowed.

At the explicit milestone, an offered-selection validator returns `TargetPlanRepresentationMismatch` for private change, following the compact validator seam. Do not promise `MixedRepresentationConservation`: Burn's sole PublicArithmetic alternative is pruned as incompatible before that case function runs (`packages/compiler/src/engine_attestation/proof.rs:320–341`), (`packages/compiler/src/operation_plan.rs:543–553`), (`packages/realization/src/declarations/burn.rs:220–231`).

A correct private-change plan needs distinct input/output selections for ReceiptLive. The existing object-keyed ExecutionCaseId, RepresentationChoiceId and engine ChoiceKey cannot express Explicit input with PrivateCommitted output. This is a real shared selection-key extension, not one small facade edit. Select four separately reviewed packets: qualified keys/cases, mixed proof/source lowering, mixed facade/validator, independent oracle/activation. The design and stop conditions are in (`sec:w3route:mixed`); the cost is 4,100–7,300 changed lines across those four packets, plus four full gates, not an unsupported promise of 700 lines. The numerical estimates are planning bounds to review before code, not observed costs.

### Q5. Typed ASH constructor closure · `proposal:w3route:closure`

Compare each independently derived producer contract (Burn-fresh, compact-aggregate, Clear-positive-residual) with both compact and Clear recognizers. Compare U, selected public representation, amount authentication, partition/family role, constructor requirements, public dependencies and required exits. Keep A, B and B−X roles distinct; require the residual constructor only on the positive branch. ObjectId equality proves too little; equality of their value formulas would be wrong (`rule:guide15:object-closure`).

The one-bound-input scope revalidates all facade sources and all six comparisons. Its unselected-obligation projection prevents lifecycle omission. Linked program/constructor equality, target capability completion and public recovery remain later-wave duties; a private-change proof must not turn fresh ASH into a creator-secret-dependent object (`plans/packages/realization.md:447`), (`rule:guide15-exec:consuming-evidence`).

### Q6. Facades, privacy and dormant entry · `proposal:w3route:facades`

Add `ValidatedBurnOperationPlan`, `ValidatedClearOperationPlan` and `ValidatedPhase7ScopePlan` as sibling compiler facades; keep `ValidatedTargetOperationPlan` as compact's public implementation. Private fields, read-only projections and fresh derivation protect validated construction. Operation-specific errors carry relevant operation/relation/case and defect; no graph handle, target type, public unchecked constructor or serialized plan identity is added (`rule:guide15:operation-plans`).

Choose the binding-seam route for dormant lowering: keep unsupported-operation checks at `input.rs:217` and `engine_attestation.rs:133–136`; remove operation checks inside case/layout/placement/source/requirement stage functions as their operation's complete lowerer lands. Internal complete owner records can then reach those stages without a test-only bypass. Body guards remain until the corresponding interpreter exists. Burn's dormant stage enables SideRepresentation, BurnBinding and DataOutputs interpretations; Clear stays publicly refused by its operation guard, and Clear-specific bodies remain refused until its dormant stage. DataOutputs dispatches by its declaration's operation. The body guard need not gain a signature parameter; source/body owners already receive operation identity.

The alternative of testing only guard-free per-body helpers would not demonstrate the carrier/layout join and would push too much unreviewed integration into activation. Convert `direct_case_entry_refuses_operations_without_plans` and source direct-entry subjects to complete internal-lowering controls, preserving public refusals until the activation/oracle bite. Record that boundary change at `plans/backlog.md:583,587`. Each facade and oracle packet may correct every lowerer it first exercises, explicitly listed in the path sets.

After both operations activate, retain `UnsupportedOperationPlan` and `UnsupportedRelationPlan` as documented reserved errors for future unsupported operations/bodies, with their diagnostic names. Do not leave tests claiming a current supported operation reaches them. Update compiler and realization READMEs at each activation; no deleted evidence is silently relabelled (`packages/compiler/src/error.rs:64–67,1558–1559`), (`packages/realization/README.md:53,618`).

### Q7. Independent finite oracles · `proposal:w3route:oracles`

Apply one rule to compact, Burn, Clear and scope: “The oracle must not use an analyzed-program field to derive the expectation for that same field.” Architecture, realization declarations and fresh exact feasible search are sanctioned sources; independent boundary/coverage expectations must not call the production derivation of the property under test (`plans/guides/guide_seven.md:1677–1725`), (`packages/compiler/src/tests/analyzed_program_oracle_tests.rs:11–29`). Literal tables are useful, but banning declaration builders would contradict the reused compact oracle.

Burn tiny domains cover absent/present sponsor, one/two receipt carriers, zero/one change role and each selected explicit/private-change alternative when it activates. Clear covers one/two ASH carriers, STATE coordinator, sponsor cases and literal branch classes full (X=B, residual inactive), partial (X<B, positive residual active), and refused-at-clamp. These compare conditional plan obligations; no 48-value arithmetic loop is presented as a plan proof. Existing realization arithmetic tests stay their own regression.

For each of at most four obligations, enumerate the power set of at most three eligible carriers: at most 8^4 = 4,096 products per tiny instance, not 81. Empty subsets test missing required carriers; exact coverage/layout/lifecycle joins retain independent expected data. Record domains, actual products, proof-plan counts, per-operation placement factors and wall. Do not multiply independent operation placement factors in production or inflate the oracle into a generic second planner (`packages/compiler/src/tests/placement_oracle_tests.rs:5–6,109–123`), (`plans/guides/guide_seven.md:56`).

## 3. Private-change design and interface ledger · `sec:w3route:mixed`

The shared proof/selection machinery is reusable, but its keys must distinguish sides. Proposed `RepresentationChoiceId` adds an optional side; existing object-level keys retain None. The owner lowers side-qualified choices to a corresponding optional qualifier in `engine_proof::ChoiceKey` and lifecycle ChoiceRecord. The generic kernel compares opaque qualified keys and does not interpret Burn. Required-choice validation remains operation-local and requires the input choice for Burn; output choice cannot repair it. Extend ExecutionCaseId with a separate side-representation map, empty for old pilots, and keep the existing object map. Append a tagged encoding only when the side map is nonempty, preserving existing case encodings byte-for-byte. Preserve the engine-base capture as well as key encodings: hand-written Debug for RepresentationChoiceId and ExecutionCaseId omits an absent qualifier or empty side map, preserving the existing derived field order, names and pretty formatting; present qualifiers remain visible. The unchanged preserve_engine_base test must reproduce all five byte lengths and SHA-256 digests in packages/compiler/tests/fixtures/engine_base/MANIFEST (`packages/compiler/src/tests/engine_base_capture.rs:155–229`). Re-baselining is rejected because it would discard the evidence that empty qualifiers preserve old identities. The capture test and MANIFEST remain read-only. No fake object ID or second selection search is introduced.

Lower Burn's input ReceiptLive {Explicit} and output ReceiptLive {Explicit,PrivateCommitted} independently; explicit Ash remains the target selection. Add side-qualified source/activation and layout representation obligations; input E/output PrivC may never become input PrivC. Existing source roles already name amount side/object. The engine's candidate lifecycle union may include both selected modes; the scope still separately retains every unselected declared obligation. A relation owns only the lifecycle rows of its own operation's selected mode for that object — the output-side choice where the object is side-qualified; plan-level completeness may keep the candidate union. Change engine_requirement::owned_lifecycle and both attestation call paths to pass the owning operation and selected qualified choices, rather than filtering only (object, exit). Candidate filtering alone retains modes chosen by any operation and cannot establish this ownership (`packages/compiler/src/engine_proof.rs:279–289`), (`packages/compiler/src/engine_requirement.rs:32–47`), (`packages/compiler/src/engine_attestation/requirement.rs:115,472–482`). Side qualification enters key types (including engine_proof::ChoiceKey, lifecycle ChoiceRecord and ExecutionCaseId) and new activation, structural/compiler requirement and layout enum variants only. Add no fields to the pinned producers' literal-built engine_cases::Case, engine_cases::Tables, engine_case_facts::Facts, engine_proof::Records or engine_program::Records (`packages/compiler/src/engine_keyed.rs:440–452,791–795,842–860`), (`packages/compiler/src/engine_keyed_fixed.rs:480–492,941–945`), (`packages/compiler/src/engine_keyed/program.rs:85`), (`packages/compiler/src/engine_keyed_fixed/program.rs:89`). No pinned producer constructs ChoiceKey or ChoiceRecord. A required new field in those records stops for a separately reviewed re-freeze packet. Update the named consumers and attestation encoders/restorers without extending those record structs. It is a bounded shared-key extension, not a new proof algorithm.

For mixed conservation, add the existing ConfidentialConservation alternative to Burn's declaration and exact alternative-validation expectation; do not add ProofKind or edit frozen relation.rs. Admit it only for the reviewed Burn tuple (input E, Ash E, change PrivC); retain PublicArithmetic for fully readable tuples. The generic `proof_supports_representation` rule is not globally weakened: attestation lowering emits incompatibility constraints for the complete Burn tuple. This deliberately admits the operation-specific route deferred by (`rule:guide13-exec:mixed-representation`) after the required ledger/review; it does not approve arbitrary mixed operations. If existing unary incompatibility constraints cannot exclude every invalid tuple, stop for a reviewed combination-constraint extension rather than accepting a cross-product silently. Burn's Ash domain remains {Explicit, PublicCommitted}, not fixed Explicit (`packages/realization/src/declarations/burn.rs:303–313`). PublicArithmetic excludes (Burn output ReceiptLive, PrivateCommitted); ConfidentialConservation excludes both (Burn output ReceiptLive, Explicit) and (Burn Ash, PublicCommitted). With normalized Explicit input these unary incompatibilities admit only E-input/E-Ash/PrivC-change for the confidential alternative. For that tuple alone, conserved_amount_visibility returns Committed and discharge is target-owned ConfidentialValueConservation; explicit amounts remain public operands of the other relations. Every other mixed case retains MixedRepresentationConservation. Reading only the object map would falsely classify this case as Readable; reading sides without this exception would refuse it (`packages/compiler/src/case.rs:124–151`), (`packages/compiler/src/placement.rs:303,381,565`), (`packages/compiler/src/coverage.rs:577,690`), (`packages/compiler/src/engine_attestation/coverage.rs:29`).

The mixed alternative's proof requirement is commitment conservation with explicit U inputs/fresh ASH and confidential change commitments, with exact recognition/partition/owner/source binding. Public shape/count/asset/recognition obligations remain carrier-owned. ConfidentialValueConservation remains external target evidence; compiler analysis never claims it executed the commitment equation. Do not require the private change scalar publicly: owner-local construction data and public commitment authentication are distinct. Event value A and fresh public ASH remain publicly bound. No new generic evidence variant is needed if the existing operation/asset ConfidentialValueConservation can express the exact source table; otherwise the missing fact returns for review. Wave 4 determines concrete proof availability and carrier fit.

Rejected alternatives: changing only the Burn facade leaves side ambiguity below it; using the output mode as the object's input choice widens admission; a virtual ReceiptLive object corrupts semantic identity; globally permitting PublicArithmetic for private modes invents an arithmetic proof; globally permitting ConfidentialConservation for every explicit family changes old owners. The selected route confines tuple policy to attestation, preserves empty keyed choice semantics and pays four reviews/gates.
