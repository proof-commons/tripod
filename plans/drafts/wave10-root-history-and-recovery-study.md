# Study: Wave 10's root-history and public-recovery substrate and its bites

Status: a design study over the tree at `0.6.254-dev`, carrying a bite-2 design addendum over the tree at `0.6.257-dev` and a bite-3 design addendum over the tree at `0.6.259-dev`, written because Wave 10's nine deliverables at (`task:guide14-exec:wave10`) are carried by thirty matrix rows that declare no evidence boundary at all, and a bite cannot be cut against a row whose verdict has no producer and no layer. Every figure below is recounted from the source or read from the assertion that pins it; nothing here was obtained by running a test, and no line of production code is changed by this file. It answers nine design questions as numbered decisions, leaves two open, and manufactures the four bites that implement the decisions. With bite 1 landed at `0.6.257-dev`, section 2.9 records what that landing fixed, sections 2.3 and 5 restate what it decided differently, and decisions D10 through D14 cut bite 2 at the level of exact shapes. With bite 2 landed at `0.6.259-dev`, section 2.10 records that landing against its own estimate, section 5's bite-2 text is restated in place at the five sentences the landed module decided differently, and decisions D15 through D19 cut bite 3 at the same level: every type with its fields and their types, every signature, every refusal variant with its operands, every test with the fact it asserts, every existing line that changes, and the gate's readings with the figure each must be.

## 0. In one breath

Wave 10's substrate is further along than its rows record: `OperationId::AnnounceMaturity` and `ProjectionId::TransitionCertificate` already exist and the compiler's plan already requires that projection of this operation, the operation's own spec already declares STATE succession as its only root use and exactly one STATE on each side, §17.3's no-migration inequality is already a named linker function, the witness already carries the static root, the leaf script and the control block that a public reconstruction needs, and the accepted archive already publishes exact mined bytes with a locator, a block hash, a height, a network identity and a genesis identity — so sixteen of §16.8's faults are decidable by a host validator over a constructed edge sequence and nine of §16.13's thirteen are mutations of a public handoff, with four proved by construction instead. What is genuinely absent is a typed edge, a typed handoff, the two reports that carry them, and — the structural blocker — an evidence boundary either report can declare: `classify` routes on a row's refusing layer, thirty rows have none, and the two standings shaped to receive them stand at zero because no boundary reaches them. The bites therefore build the edge validator, the checkpoint binding and its registry, the handoff and the process constrained to receive it, and close by landing the two validated reports, minting the two boundary members on the precedent this workspace has already set twice, retyping the thirty rows and recounting the census from 41 answered to 71.

## 1. The problem, exactly

§14.6 defines the root-history report as an ordered typed edge sequence of `StateRootEdge { predecessor: StateOutpoint, successor: StateOutpoint, operation: OperationId, certificate: TransitionCertificate }`, says "The report validates every edge in order" and says "Final cursor equality is insufficient" (`plans/guides/guide_fourteen.md:2246–2261`). §14.7 defines the public-recovery report as "produced by an unrelated process or a process constrained to receive only the public handoff" and lists eleven items it records (`plans/guides/guide_fourteen.md:2263–2279`). §17.1 gives the validator six clauses and fixes the expected sequence for a single announcement at "exactly one member" (`plans/guides/guide_fourteen.md:2716–2729`); §17.2 binds ten facts and states that "A reorg that removes or changes the transaction stales the observation" and that "Evidence from another chain prefix is not silently reused" (`plans/guides/guide_fourteen.md:2731–2748`); §17.3 states the no-migration inequality (`plans/guides/guide_fourteen.md:2750–2758`).

Of the four types §14.6 names, one is absent from the workspace and three are not. `StateRootEdge` occurs in no Rust file. `StateOutpoint` occurs as no type either; what the tree carries is `transaction::bytes::Outpoint` and the view entry `MaturityViewEntry::CurrentStateOutpoint` (`packages/transaction/src/state_view.rs:84`). `OperationId` is an existing thirteen-member identifier whose thirteenth is `AnnounceMaturity` (`packages/architecture/src/ids.rs:112`). `TransitionCertificate` exists as the first member of `ProjectionId`, "Derived history projections" (`packages/architecture/src/ids.rs:298–306`) — and it is not decorative: the architecture's comment above the projection specs says "Every accepted modeled transaction induces one transition certificate" (`packages/architecture/src/spec.rs:649–651`), the announce-maturity operation declares `projections: PROJECTION_TRANSITION` (`:1662`), and the compiler's announcement plan names it `REQUIRED_PROJECTION` (`packages/compiler/src/maturity_announcement_plan.rs:61`). §3.1's ground table already assigns the subject: "transition certificate | architecture/model/realization boundary" (`plans/guides/guide_fourteen.md:717`). The identifier and the requirement exist; the value the report carries does not.

The same asymmetry holds for §17.1's six clauses. Four of the sixteen §16.8 faults are refused today by code that has nothing to do with history: the projector requires exactly one input and exactly one output and names each failure (`packages/vectors/src/maturity_continuity.rs:595–604`), the operation's own spec bounds STATE at `MaxCount::Exact(1)` on both sides (`packages/architecture/src/spec.rs:1618–1641`), STATE's object spec carries `deallocators: &[DeallocatorId::None]` (`:2091`), and the operation's root use is `ROOTS_STATE_ONLY` with `RootUse::Succession` (`:619–622`, `:1615`) beside `issuances: NO_ISSUANCE`, `canonical_deltas: NO_DELTAS`, `data_outputs: NO_DATA_OUTPUTS` and `writes: &[]` (`:1616`, `:1643–1647`). §17.3 is not merely implementable but implemented: `state_bundle_continuity` is the no-migration rule written once, documented as "the single assertion a migration relation would replace", and the continuity projector already calls it (`packages/linker/src/state_bundle.rs:375–410`, `packages/vectors/src/maturity_continuity.rs:1614`).

For §14.7 the tree is further still. The witness stack is nine items of declared widths, and the projector reads the static root from item three, the linked leaf script from item seven and the control block from item eight, comparing each against the retained recipe (`packages/vectors/src/maturity_continuity.rs:591–621`, `:1542`, `:1549`, `:1558`); the successor's reconstructed program is compared against `transaction.outputs()[0].program()` (`:1587–1590`). The accepted archive carries exact mined bytes, both identities, a block hash and a height in `MaturityAcceptedReadback` (`packages/vectors/src/maturity_native.rs:176–214`), and its RUN-REPORT publishes a network identity, a genesis identity and a target contract (`packages/vectors/src/maturity_corpus.rs:395–412`, parsed from `packages/vectors/fixtures/maturity-variable-run-of-record/RUN-REPORT`). A process holding those bytes and that locator holds every §14.7 item bar the deployment parameters that bound the lead window and the nonce search.

What blocks all of it is one structural fact about the classifier, and it is not a missing report. `classify` reads `row.refusing_layer()`, and a row whose boundary is a typed non-answer returns `None` and is classified `OutstandingUnderTypedNonAnswer` before any evidence is consulted (`packages/vectors/src/maturity_evidence.rs:2070–2074`). Thirty rows are in that position: the sixteen §16.8 rows under `Bound::RootHistoryAnsweredByAnotherWavesReport` and the fourteen under `Bound::PublicRecoveryAnsweredByAnotherWave`, pinned at sixteen and fourteen by `each_typed_non_answer_stands_on_exactly_the_rows_its_reason_names` (`packages/vectors/src/maturity_safety.rs:3808`, `:3810`), the fourteenth being §16.1's positive row `public-successor-recovery` (`:1460–1464`, admitted by the same test's section check at `:3844–3849`). The two standings those rows would take — `RootHistoryObserved` and `PublicRecoveryObserved` — exist, are answered, are counted by `census_from_rows` and are summed by `answered()` (`packages/vectors/src/maturity_evidence.rs:1197`, `:1202`, `:1269–1281`, `:2170–2171`, `:1443–1452`), and stand at zero (`:2832–2833`). `EvidenceBoundary` has thirteen members and not one of them names a root-history or a public-recovery report (`packages/vectors/src/matrix.rs:220–265`). The vocabulary to receive the evidence is complete; the route to it is absent.

Two sentences in the tree are falsified by what the tree now holds, and both are load-bearing. The recovery reason reads "Nothing in this tree publishes one, so the row's carrier does not exist yet and a declared boundary would name a layer no candidate reaches" (`packages/vectors/src/maturity_safety.rs:264–270`), and §16.13's table comment repeats it (`:3219–3226`). Under the reading "public bytes with a locator exist" the sentence is false since the accepted archive was admitted on `0.6.245-dev`: `MaturityAcceptedReadback` carries the exact mined bytes and `MaturityByteSource::ArchivedSubmission` carries the run address as a locator (`packages/vectors/src/maturity_continuity.rs:181–189`). Under the reading "a handoff a second process can receive" it is still true, because no type in the workspace is the public handoff and no process is constrained to receive only it. The root-history reason reads "Answering a root-history row needs a typed branch context — projection, rewind and reprojection over the root cursor — that this wave has no way to observe" (`packages/vectors/src/maturity_safety.rs:249–255`), and the registry's reason repeats it as `BranchIndexedHistoryIsNotProjectable` (`packages/vectors/src/maturity_evidence.rs:517–527`). Projection, rewind and reprojection over a modelled branch are in the tree twice: `ModelIndexerCheckpoint` is an opaque cache creatable only from an already-validated reference index, under the rule "A reorg produces a fresh reference index with a different canonical burn/clear set and event order; its checkpoint is a new opaque cache" (`packages/model/src/ledger.rs:1790–1809`), and the operator-right registry carries `reorganize` beside two typed reorganization refusals (`packages/transaction/src/operator_right.rs:432`, `:510`, `:795`). What no layer here observes is a chain, which is a narrower statement than the reason makes.

## 3. Decisions

**D1. The edge sequence is owned by the vectors crate beside the continuity projector; `StateOutpoint` is `Outpoint`, `OperationId` is the architecture's existing enum, and `TransitionCertificate` is the one new value — its identifier already existing as `ProjectionId::TransitionCertificate`, which the compiler's plan already requires of this operation.** Ownership follows what an edge is: a claim recomputed over projected bytes, not an input a caller offers to construction. The transaction crate refuses to hold it on its own stated grounds — its public view "checks the one relation among them that can be checked from the entries alone" (`packages/transaction/src/state_view.rs:11–14`) and names freshness as a residual because "no layer in this crate observes a chain" (`:55–66`) — and the linker holds recipes, not verdicts. The vectors crate is where exact-byte projection already lives and where the continuity report already renders a separate evidence role (`packages/vectors/src/maturity_continuity_report.rs:49–63`). On the field types, minting new spellings would be the error this workspace has already corrected twice: `Outpoint` is the tree's outpoint and `MaturityViewEntry::CurrentStateOutpoint` already names a STATE one (`packages/transaction/src/state_view.rs:84`); `OperationId::AnnounceMaturity` is the operation (`packages/architecture/src/ids.rs:112`); and `ProjectionId::TransitionCertificate` is not a coincidence of naming but the architecture's own requirement, declared on the operation as `projections: PROJECTION_TRANSITION` (`packages/architecture/src/spec.rs:1662`) under the comment "Every accepted modeled transaction induces one transition certificate" (`:649–651`) and read by the compiler as `REQUIRED_PROJECTION` (`packages/compiler/src/maturity_announcement_plan.rs:61`). The certificate value therefore carries that identifier rather than a fresh one, and §3.1's ground table already places its subject at the "architecture/model/realization boundary" (`plans/guides/guide_fourteen.md:717`).

**D2. An edge is validated against §17.1's six clauses, §17.3's inequality and the operation's own declared root and cardinality contract, and all sixteen §16.8 faults are decidable by a host validator over a sequence constructed from the two admitted archives and the node-free candidate.** Section 2.3 names the deciding rule row by row; three of them are already refused by landed code on other grounds — `Refusal::InputCount` and `Refusal::OutputCount` (`packages/vectors/src/maturity_continuity.rs:595–604`) and `state_bundle_continuity` (`packages/linker/src/state_bundle.rs:399–410`) — and four more are decided by declarations the architecture already carries: STATE's `deallocators: &[DeallocatorId::None]` (`packages/architecture/src/spec.rs:2091`) and `ROOTS_STATE_ONLY` with `RootUse::Succession` (`:619–622`, `:1615`), which is also §23's fourteenth conjunct at (`gate:guide14-exec:exit`). The case that carries the wave's second exit is `successor-cursor-restored-after-invalid-intermediate-edge`: a three-edge sequence whose middle edge fails clause 4 and whose final cursor equals the honest successor must refuse, which is §14.6's "Final cursor equality is insufficient" and §1.14's inequality "final root cursor matched ≠ every intermediate root edge valid" (`plans/guides/guide_fourteen.md:2261`, `:443–445`). Against this decision stands the chain reading of two rows: `stale-predecessor` and `wrong-current-root-view` can mean "the stated cursor is not the chain's current root", which no layer here observes. That reading is not discarded — it is carried as the report's residual, on the precedent of `MaturityViewResidual::CurrentStateRootFreshness`, whose doc says "Naming the gap is the whole of what this layer can honestly do about it: an unnamed residual reads as a discharged one" (`packages/transaction/src/state_view.rs:221–233`). A row is answered by the structural clause it names; the report states in its own bytes what the structural clause does not reach.

**D3. The caller-stated `BranchContext` becomes an evidenced binding by pairing it with a typed checkpoint that carries §17.2's ten facts — eight read from the admitted archive and the public bytes, two declared as premises with typed provenance — and the staling verdict is produced by a modelled rewind and reprojection, not by a chain observation.** Section 2.4 assigns each of the ten. The premise form is already in the tree and already reasoned: `MaturityDisclosedFeeFloors` is carried as a declaration because "The immutable RUN-REPORT grammar carries no fee line, so archive admission cannot verify these values", with `MaturityPremiseProvenance` naming the source (`packages/vectors/src/maturity_corpus.rs:138–155`). The rewind is not invented here either: `ModelIndexerCheckpoint`'s fields are private so that "a checkpoint can only originate from an already-projected reference index and can never be assembled from arbitrary caller rows", under the rule that "A reorg produces a fresh reference index with a different canonical burn/clear set and event order; its checkpoint is a new opaque cache" (`packages/model/src/ledger.rs:751–753`, `:1802–1809`), and the operator-right registry already carries `reorganize` with two typed refusals that name reorganization as what invalidated a branch context and a scope (`packages/transaction/src/operator_right.rs:432`, `:510`, `:795`). What this discharges is §17.2's binding and its "Evidence from another chain prefix is not silently reused" over a modelled branch; what it does not discharge is chain observation, which stays the residual of D8 and keeps `BranchContext`'s own doc true — "Callers must establish the branch and checkpoint externally" (`packages/transaction/src/operator_right.rs:23–26`).

**D4. The root-history mutation registry is populated with the sixteen §16.8 mutations through a crate-private constructor, its standing becomes a function of its content, and the outstanding reason is retired rather than narrowed.** The registry already holds the right vocabulary — `MaturityRegisteredMutation { section, row, locator }`, chosen so that "a registry entry naming a locator this workspace does not otherwise use would be a second vocabulary for the same facts" (`packages/vectors/src/maturity_evidence.rs:551–585`) — and every §16.8 row already carries `Loc::RootHistoryEdge`, which `MaturityMutationLocator::subject` maps to `MaturityMutationSubject::RootHistory` (`packages/vectors/src/maturity_safety.rs:662`). Two things change together. The absence of a public constructor is deliberate and is what makes the emptiness "a property of the type rather than a claim about a list" (`packages/vectors/src/maturity_evidence.rs:557–559`); the constructor therefore becomes crate-private and is reachable only from the derivation that has already read the landed validator, which is `CanonicalSubject::admit`'s discipline applied to a registry (`packages/vectors/src/subject.rs:56–71`). And `census()` currently returns `OutstandingUntilItsMaterialLands` for any content (`packages/vectors/src/maturity_evidence.rs:648–655`), which would report a populated registry as outstanding; the standing gains a landed member and is read from the mutation list. `BranchIndexedHistoryIsNotProjectable` is retired rather than reworded because its stated ground — that no typed branch context can be projected, rewound and reprojected — is what D3 supplies; a narrowed reason would keep the registry outstanding for a fact the registry does not index, since a root-history *mutation* is relative to a sequence, and the sequence is the validator's, not a chain's.

**D5. The process boundary is a typed handoff value whose fields are exactly §14.7's public inputs, consumed by a recovery function that names no other type, exercised from an integration binary that imports neither the linker bundle nor the deployment identity nor the planner.** The strongest available proof would be a separate crate, and this study states plainly what the chosen boundary costs against it: a crate boundary makes the private types unnameable by the compiler, while a function signature makes them merely unnamed, so a later edit could widen the signature where it could not widen a dependency list. The typed handoff is chosen because the workspace already reasons this way and the weaker link is visible rather than hidden: the handoff's fields are the whole of its input, the recovery function takes the handoff by value and nothing else, and the binary's import list is a one-line gate a reviewer reads. The house form exists — `live_handoff.rs` is "The owner-sighash handoff: four states, four refusals, and no digest", a module whose whole purpose is that an order and a boundary are enforced by types (`packages/transaction/src/live_handoff.rs:1–24`) — and the crate-private admission precedent is `CanonicalSubject::admit` (`packages/vectors/src/subject.rs:56–71`). On what counts as creator-private: §16.13 answers it by naming three things — process memory, a temporary file, a wallet descriptor (`plans/guides/guide_fourteen.md:2706–2708`) — none of which is a published deployment artifact. The line therefore falls inside `CandidateLinkedMaturityBundle`, not around it: `instances: Vec<StateRetainedConstructor>` is the creator's retained pair (`packages/linker/src/state_bundle.rs:354–357`, `:512`) and `retained_context` is the projector path that requires it together with the caller's deployment identity (`packages/vectors/src/maturity_continuity.rs:671–694`), while the deployment's published parameters are the facts the construction-side public view already calls public (`packages/transaction/src/state_view.rs:5–9`). The handoff carries the published deployment parameters reconstruction needs — the witness schedule, the lead bounds and the target contract revision — and carries no instance, no identity and no planner.

**D6. The eleven items map onto existing producers for ten of them, and what the recovery report compares is the program derived from the witness against the program in output 0 of the same bytes; equality establishes that this transaction's successor is reconstructible from public data, and nothing about freshness or origin.** Section 2.5 assigns each item. The claim that the derivation needs nothing creator-private rests on where the operands sit: the static root is witness item three, the linked leaf script is item seven and the control block — which carries the internal key and the parity — is item eight, and the projector reads all three from the stack before it compares them with the retained recipe (`packages/vectors/src/maturity_continuity.rs:1542`, `:1549`, `:1558`). The metadata is item four, decoded through the schedule and `closure_target()` rather than through the bundle (`packages/vectors/src/maturity_continuity.rs:637–669`); the requested cycle is item two and the successor nonce item one (`packages/vectors/src/maturity_continuity.rs:1767–1775`). So the recovery path reconstructs from the witness and compares against `transaction.outputs()[0].program()` (`packages/vectors/src/maturity_continuity.rs:1587–1590`), and the three things it must be given beyond the bytes are the witness schedule, the lead bounds and the target contract revision, each a published deployment fact. What equality establishes is bounded twice over: §1.14 keeps public successor recovery as the seventh of eleven separate evidence classes and states "No one report silently satisfies another" (`plans/guides/guide_fourteen.md:414–430`), and §23's fifteenth conjunct keeps safety, continuity, history, recovery and resources apart at (`gate:guide14-exec:exit`).

**D7. Nine of §16.13's faults are mutations a constrained process refuses and four are proved by construction; and a refusal from that process answers its row, because unlike the continuity mutants these rows declare no target layer and their carrier is the report itself.** Section 2.6 assigns each of the thirteen. The standing question is where this decision departs from D1 of the accepted-byte classification study, and the departure is exact rather than convenient. The continuity mutants are experimental because the rows they would answer declare target layers — `ScriptPathRejection`, `LinkerRejection`, `ConstructorDerivationRejection` — that a host projector is not, so a host refusal over them would answer a question the declared layer was never asked (`plans/drafts/accepted-byte-classification-study.md:95–106`). The §16.13 rows declare no layer at all, their control is "The published announcement transaction a recovery reads back" (`packages/vectors/src/maturity_safety.rs:414–415`) and their carrier is `Report`, documented as "Current-root freshness, the root-history edge sequence, and public reconstruction" (`:331–333`). §14.7 settles the rest by defining the producer: the report is "produced by an unrelated process or a process constrained to receive only the public handoff" (`plans/guides/guide_fourteen.md:2265`) — a definition that names no target and could not be satisfied by one. The carrier is therefore reachable, and the same argument carries §16.8: `RootHistoryObserved` and `PublicRecoveryObserved` exist because §14.2 names classes six and seven (`plans/guides/guide_fourteen.md:2157–2172`), and a class whose producer this study builds stops being a class with no row.

**D8. The reports carry three synthetic-origin non-claims as typed residuals: no chain observation, no freshness of the root cursor, and no origin of the archive beyond its admission.** Residuals rather than prose, because the continuity report already fixes the form and already carries the nearest neighbour of the second — `CallerStatedBranchWithoutFreshness`, "Branch operands are caller-stated context, not a freshness proof" — with a validator item per residual position (`packages/vectors/src/maturity_continuity_report.rs:86–116`, `:1397–1404`). The third is the one this study adds to the vocabulary: the accepted archive's bytes are admitted through pinned file names, sizes and digests (`packages/vectors/src/maturity_corpus.rs:193–205`), which establishes that these are the bytes that were captured and establishes nothing about how the predecessor they spend came to exist. Stating it is what keeps the recovery report from reading as a provenance claim, and the ground is the same one the public view states about its own gap: an unnamed residual reads as a discharged one (`packages/transaction/src/state_view.rs:229–232`).

**D9. §16.1's four-term row is one row.** The guide numbers §16.1's required cases one to fourteen and states the fourteenth as a single conjunction, "accepted target transaction with semantic, constructor, root, and recovery projections all matching" (`plans/guides/guide_fourteen.md:2443–2456`); the matrix transcribes fourteen positive rows and `CONTROL_AGAINST_SUBJECT` recounts them at fourteen (`packages/vectors/src/maturity_safety.rs:3560`). The case for splitting is real and is recorded here rather than dismissed: the term vocabulary exists precisely because "a row that expects one of them to differ is making a different claim from a row that expects another" (`packages/vectors/src/maturity_safety.rs:674–691`), four rows would give each of the four reports exactly one row to answer, and that is the shape `ConstructorContinuityObserved`, `RootHistoryObserved` and `PublicRecoveryObserved` were built for. It loses on two counts. §16 is transcribed rather than designed in this workspace, and a row the guide states as one numbered item is not this workspace's to divide while the guide states it that way; and the split would move the denominator from 206, against which the census, the register and the completeness figure are all pinned (`packages/vectors/src/maturity_evidence.rs:3342`, `:3353–3361`), to buy a distinction the projection terms already make inside one row. What changes under this study is not the row's arity but its blocker: with producers for the root-history and public-recovery terms, the row's remaining obstacle is the acceptance its boundary names, `Bound::AcceptanceAwaitsRelayAdmissibility` (`packages/vectors/src/maturity_safety.rs:1470–1474`), which is the accepted-byte classification study's own first open question rather than this one (`plans/drafts/accepted-byte-classification-study.md:182`).

**D10. The checkpoint is one value carrying §17.2's ten facts beside the branch the validated continuity already states, minted by a single fallible constructor that reads the accepted archive's readback and then asks the binding question; the binding question is a typed result naming the disagreeing fact and both operands, never a boolean.** Eleven private fields and no `Option` among them: three owned `String`s for the report facts, `block_hash: Digest32`, `block_height: u32`, `transaction_identity: Txid`, `predecessor: Outpoint`, `successor: Outpoint`, the two declared premises, and `branch: BranchContext`. The eleventh field is read from `continuity.branch()` (`packages/vectors/src/maturity_continuity.rs:2093`) rather than taken as a second caller statement, because the continuity already carries the caller's branch and a second statement of it could differ from the first — one rule with two implementations is how wrong-boundary rows came to stand as answered before (`packages/vectors/src/maturity_evidence.rs:1241–1249`). The readback is read from the admitted corpus rather than from the continuity, because the continuity's own obligation is a caller-supplied claim the projector has already verified against the same bytes and the same recomputed identities (`packages/vectors/src/maturity_continuity.rs:1658–1707`), so reading it there would ask a question already answered, while nothing in the tree compares an archive's obligation with an arbitrary continuity. The archive whose obligation is `Outstanding { routes }` therefore refuses at the first step, which is the shape a checkpoint refusal has to have: the historical archive stands exactly there, pinned by `the_positive_row_names_the_accepted_run_and_its_disclosed_environment` (`packages/vectors/src/maturity_evidence.rs:3410–3418`), and the accepted archive's `Established { schedule, identity, readback }` is pinned by the same test at `:3370–3402`. The binding question returns `Result<(), MaturityRootCheckpointRefusal>` because every refusal in this module retains both operands (`packages/vectors/src/maturity_history.rs:174–211`) and a boolean discards them; the same variants serve the constructor's cross-checks and the binding question, because they are one comparison asked at two moments rather than two comparisons that could drift apart.

The ten facts are named by one enum and typed by a second with a total `const` mapping, so that which facts a checkpoint verifies and which it merely carries is a value rather than a sentence.** Section 2.4 is that mapping's content: six facts are carried by the admitted archive, one is read from the public bytes, one is derived from the public bytes and the locator, and two are declared premises carrying their `MaturityPremiseProvenance`. The mapping is written as an exhaustive match with no fallback arm, on the ground `MaturityMutationLocator::subject` states for itself — a member minted later cannot compile until somebody states what it is, and a wildcard would answer that question by accident for every member added after it (`packages/vectors/src/maturity_safety.rs:636–672`). A checkpoint that carried the ten facts without their kinds would read as ten checked bindings, which is precisely what §17.2's ninth and tenth facts are not, and what the study's fourth exit records as NOT MET for the root-history path. The kind enum's fourth member carries the provenance rather than standing beside it, so a premise cannot be rendered without saying where it came from.

**D12. A declared premise is one generic carrier holding a value and a provenance, the new provenance member names the caller's deployment declaration, and each premise carries its whole value.** The carrier lives in `packages/vectors/src/maturity_corpus.rs` beside `MaturityDisclosedFeeFloors`, whose `declared(..)` and `provenance()` are the house form for a fact archive admission cannot check (`packages/vectors/src/maturity_corpus.rs:145–185`), and the generic single-field wrapper is `CanonicalSubject`'s own shape (`packages/vectors/src/subject.rs:54–72`). One carrier rather than two concrete types, because the two premises differ only in payload and two types would state the same rule twice. Each carries its whole value rather than an identifying projection, because "the archive pins nothing about them" means there is nothing archive-side for a projection to be compared against; what a later reader does compare is the evidence plan's own `bundle()` and `abi()` (`packages/vectors/src/maturity_evidence.rs:1536`, `:1543`), and both of those are whole values. The consequence is stated rather than hidden: a checkpoint carrying the whole linked candidate carries `instances`, the creator's retained pair (`packages/linker/src/state_bundle.rs:512`), so the checkpoint is not a public handoff and makes no claim about creator-private state — that claim is bite 3's, over a type whose fields cannot name an instance, and the study's fourth exit already records the root-history path as NOT MET on exactly this ground. `MaturityPremiseProvenance` is matched nowhere in the workspace and carries no exhaustive reader, so its second member is additive.

**D13. The modelled branch is a prefix of modelled blocks anchored at the checkpoint's own block; rewind and extension are side-effect-free functions returning a new prefix, reprojection returns an observation or a typed stale verdict, and evidence from another prefix is refused before any height is read.** A prefix carries its anchor identity, its anchor height and its blocks, so "which branch this is" is structural rather than recomputed, and the derived `BranchContext` is the anchor identity at the tip height — the identifier answering which branch and the ordinal answering how far along, which is what `BranchContext`'s two fields already mean (`packages/transaction/src/operator_right.rs:28–31`). Both movements take the prefix by reference and return a new one, so a refusal leaves every operand intact and two prefixes can be held side by side, which is what the reuse case needs; the tree's `reorganize` mutates in place because it owns a registry of issued scopes (`packages/transaction/src/operator_right.rs:795–809`), and a model with no registry has no such obligation. Reprojection compares the prefix's identifier against the checkpoint's stated branch first, because reading a height out of a prefix the evidence did not come from is the silent reuse §17.2 forbids; only then does it read the block at the checkpoint's height, so the two stale outcomes are the removal of that block by a rewind and a changed block at that height, the second splitting into a changed block identity and a transaction the changed block does not carry. Each is a refusal variant with both operands, and no new type carries an `Option` field. What a modelled prefix is not is stated in the module beside it: it observes no chain, so it is not a chain view and its tip is not a freshness claim — the model's blocks are the caller's, which is D8's first and second residual and keeps `BranchContext`'s own doc true, "Callers must establish the branch and checkpoint externally" (`packages/transaction/src/operator_right.rs:25–26`). The precedent for a cache that can only originate from an already-validated projection is `ModelIndexerCheckpoint` and the reprojection rule beside it, "A reorg produces a fresh reference index with a different canonical burn/clear set and event order; its checkpoint is a new opaque cache" (`packages/model/src/ledger.rs:749–759`, `:1802–1809`).

**D14. The registry's entries are derived from the matrix rows its kind names, its standing is read from its content in both directions, the outstanding reason is removed together with its mapping, and the type drops `Outstanding` from its name.** The constructor takes the kind and nothing else: the section and the locator that kind names are two `const` mappings beside it, and the entries are the rows of that section whose locator is that locator, collected rather than listed — a listed sixteen would be a second statement of the table's width, which is the failure `census()` already names about figures kept next to tables (`packages/vectors/src/maturity_safety.rs:3393–3397`). It carries no visibility modifier, exactly as `outstanding` carries none (`packages/vectors/src/maturity_evidence.rs:622`), so it is reachable only from inside the module that derives the plan — stronger than `CanonicalSubject::admit`'s `pub(crate)` (`packages/vectors/src/subject.rs:64–72`) and the same discipline. This is D4's "reachable only from the derivation that has already read the landed validator" in its reachability reading: the constructor takes no validator argument and needs none, because what makes a §16.8 row a registered mutation is that the row exists in the matrix with that locator, and what makes the registry's material landed is that the validator those rows are mutations of is in the tree — a fact about the module, not an operand. The reason is retired rather than narrowed because its stated ground is that no typed branch context can be projected, rewound and reprojected, which D13 supplies; and `census()` reads `OutstandingUntilItsMaterialLands` for an empty list and `RegisteredAgainstTheLandedMaterial` for a non-empty one, so the count and the standing cannot disagree. The rename follows from that same rule: a type named for a standing its own census computes would state a standing the census can contradict, and the kind enum keeps its name because which registry this is does not change with its content.

**D15. The handoff's fields are §14.7's three public inputs and the five published deployment parameters a reconstruction needs, and the locator is one typed value carrying both the archive's run address and the identity the bytes must recompute to.** §14.7's input side is the locator, the exact bytes and the STATE output index; the witness fields are read from the bytes rather than handed over. Everything else a reconstruction reads is a deployment fact the deployment publishes, and the tree names which: `state_output_program_at_nonce` takes the reviewed target, the encoded metadata, a whole `StateStaticSubtree` and a `StateInternalKeyPolicy` (`packages/tapscript/src/state_constructor.rs:1141–1152`), the metadata is decoded under a `StateWitnessSchedule`, and the successor's semantics are derived under `AnnouncementLeadBounds`. Section 2.5's reading that the witness carries the subtree and the internal key at items three and eight is exact for the root and not for the subtree: item three is the 32-byte static root, while the subtree the primitive requires carries its leaves and is walked by `validate_static_paths` (`packages/tapscript/src/state_constructor.rs:1079–1090`), so a root cannot stand in for it. The five are published rather than retained: `packages/transaction/src/state_view.rs:5–9` calls the accepted linked bundle public with "no operator secret here, no scalar, and no field one could be put in", and §16.13 names the creator-private dependencies as process memory, a temporary file and a wallet descriptor (`plans/guides/guide_fourteen.md:2706–2708`) — a taptree, an internal key, a witness schedule, a lead window and a contract revision are none of those. Carrying them cannot manufacture a false verdict, which is the decisive point: a wrong subtree, key or window reconstructs a program that differs from output 0, so the equality is self-validating in exactly the direction that matters. The locator is one value rather than two fields because §16.13's `copied-transaction-bytes` is a comparison and a comparison needs a stated side: `MaturityByteSource::ArchivedSubmission { run_address }` is the tree's own locator vocabulary (`packages/vectors/src/maturity_continuity.rs:185–188`) and carries a content address explicitly documented as "not an accepted transaction identity", so the identity the bytes must recompute to is the locator's second field. The contract revision is carried and recorded rather than compared, because the reconstruction runs under the one reviewed contract `closure_target()` publishes (`packages/vectors/src/maturity_closure.rs:528–534`) and §16.13 names no fault for a stated revision: a refusal no row can receive is a verdict without a question, which is the failure `EvidenceBoundary`'s own doc records (`packages/vectors/src/matrix.rs:209–210`).

**D16. The recovery reaches every §14.7 reading from the handoff through published primitives, and the continuity module's diff is three functions gaining `pub(crate)` and nothing else; the bundle-taking reconstruction and the leastness search keep their signatures because the public path needs neither.** Three readings are already public and already used outside the projector: `state_output_program_at_nonce` (`packages/tapscript/src/state_constructor.rs:1141`), `announce_maturity` (`packages/realization/src/state.rs:315–319`) and `closure_target` — the integration binary beside this one calls the first two directly (`packages/vectors/tests/maturity_continuity.rs:463–481`). Two are private and take only public values, so they gain `pub(crate)` with their signatures unchanged: `witness` (`packages/vectors/src/maturity_continuity.rs:591–594`), which takes the decoded transaction and the schedule, and `decoded_witness_metadata` (`:637–641`), which takes the stack, the schedule and the reviewed target — the projector's own proof that the metadata decode needs no bundle. The third is `MaturityByteComparison::new` (`:228`), private today, which the recovery needs because the equality result §14.7 records is a byte comparison and the tree has one type for exact named byte operands (`:222–252`); minting a second would be the second vocabulary D1 refused. Against this stands the signature change that would make the projector's own reconstruction public: `fixed_projection` reads exactly `bundle.static_subtree()` and `bundle.policy().internal_key()` from the bundle (`:754–755`), so `fn fixed_projection(target: &ReviewedElementsTapscriptDefinition, encoded: EncodedStateMetadata, static_subtree: &StateStaticSubtree, policy: StateInternalKeyPolicy, side: TransactionSide)` and the same replacement on `reconstruct` (`:811–816`), `leastness` (`:823–829`) and `search_leastness` (`:836–842`) would carry public values throughout. It is rejected on cost and on need. The cost is every call site of the four: production at `:817`, `:830`, `:1755`, `:1757–1763`, `:1776–1781` and `:1792–1798`, and test call sites at `:2816`, `:2826`, `:3277`, `:3506`, `:4029`, `:4071`, `:4328` and `:4412` — more than a dozen production lines to change in a module this bite otherwise does not touch. The need is absent in both directions: the leastness search claims a property this recovery does not claim, and the primitive's own doc says why the fixed commitment is the public one — "The representation nonce is the caller's, committed as named instead of searched for, which is what lets a party holding a published program check the program against the metadata and nonce it was given" (`packages/tapscript/src/state_constructor.rs:1126–1134`); and the fixed projection's outputs beyond the program are the field commitments and the control recipe, and the recovery reaches the one binding it needs from the control block's own bytes.

**D17. `recover_public_successor` runs nine steps in first-refusal order over a handoff taken by value, and a reconstructed program that differs from output 0 refuses rather than returning a recovered successor carrying a false equality.** The order is the projector's, minus everything the bundle owns: decode the bytes; recompute the identity against the locator; read the witness at the STATE input; check the witnessed static root against the published subtree; decode the predecessor metadata and bind it to the control block; derive the successor semantics at the witnessed cycle under the published lead window; commit them at the witnessed representation nonce; read the actual program at the stated index; compare. First refusal rather than accumulated verdicts is the module's rule throughout (`packages/vectors/src/maturity_continuity.rs:1741–1798`), and it is what makes each §16.13 row answerable on its own axis: a mutation that reached a later comparison would be answered by a later row's refusal. The disagreement refuses because §2.6 reads `reconstructed-program-differs-from-chain-output` as a mutation, and a mutation row is answered by a refusal; a `RecoveredSuccessor` carrying `agrees() == false` would be a value whose own name is false, and the report that consumes it would have to decide, a second time and elsewhere, what the recovery already knows. The comparison is still carried on the validating path, because §14.7 records the equality result as an item and a report that cannot state its operands states a verdict instead of evidence. The eleventh item, the absence of creator-private dependencies, is carried by no field: a value asserting its own purity proves nothing about what its module imported, and the four construction proofs of D19 are what the item actually names.

**D18. `MaturityRecoveryRefusal` has nine variants, one per §16.13 mutation, each retaining both sides of what it compared, with a total `const fn row` naming the row it answers.** Nine variants and nine rows is the exhaustiveness this bite's gate reads, on the shape `HistoryClause::label` and `MaturityRootHistoryRefusal::clause` already have (`packages/vectors/src/maturity_history.rs:164–169`, `:224–238`): a mapping written as a match with no fallback arm means a tenth variant cannot compile until somebody states which row it answers, and a refusal that answers no row is the verdict-without-a-question D15 refuses. Two of section 2.6's mechanism readings are recounted here against the handoff's input side. `stale-successor` reads there as a mutation "against the stated successor outpoint", but §14.7's input side states no successor outpoint — the successor is derived from the locator's identity and the stated index — so the axis a constrained process can actually mutate is the witnessed cycle against the published lead window, which is where `announce_maturity` refuses (`packages/realization/src/state.rs:315–319`); the chain reading of the row, that the successor has since been spent, is D8's freshness residual exactly as section 2.6 says. `wrong-static-subtree` reads there as item three "altered against the control path", and the public comparison the tree actually supports is item three against the published subtree's root, which is the comparison the projector makes against the retained one (`packages/vectors/src/maturity_continuity.rs:1542`). Both keep section 2.6's classification as mutations; only the operand each mutation moves is restated. `missing-representation-nonce` and `malformed-public-witness` are separated by reading which item the witness refusal names rather than by a second parse: a width refusal at item one is the nonce's absence, and every other witness refusal is malformation — one primitive, two rows, no second implementation.

**D19. The four construction proofs are one roster enum with a total item mapping, one function-pointer assertion, and one import-list assertion in the integration binary, so each is a fact about a type or a file rather than an assertion about a value.** A value proves nothing here: a handoff that happens to hold no descriptor says nothing about the handoff a later edit could hold one in. `PublicHandoffInput` with `ALL` and a total `const fn item` is the shape D11 already chose for the checkpoint's facts and the ground `MaturityMutationLocator::subject` states for itself — a member minted later cannot compile until somebody states what it is, and a wildcard would answer that question by accident (`packages/vectors/src/maturity_safety.rs:636–672`). A test that asserts the handoff's field count equals `ALL.len()` and that no member names a retained instance, a deployment identity, a descriptor, a key or a path turns "the handoff names none of these" into a statement the compiler and one length assertion jointly enforce. The function-pointer assertion is the same discipline for the function: a `fn(PublicAnnouncementHandoff) -> Result<RecoveredSuccessor, MaturityRecoveryRefusal>` binding fails to compile if a second parameter is ever added, which is what "consumed by a function taking it alone" means operationally. The import list is the weakest of the four and D5 already says so: the binary reads its own source through `include_str!` and compares its `use` lines with a literal list, so a widening is a diff in the test rather than a silent dependency. Against a crate boundary all four remain weaker, which is why the third exit stands CONDITIONALLY MET rather than MET.

## 4. Open questions

**OQ1. Whether §16.8's `stale-predecessor` and `wrong-current-root-view` are structural rows or chain rows.** §16.8 lists both without saying which cursor they are stale or wrong against (`plans/guides/guide_fourteen.md:2583–2584`), and §17.1's first clause is structural — "predecessor equals the current cursor before the edge" (`:2724`) — while §17.2's "A reorg that removes or changes the transaction stales the observation" is not (`:2746`). For the structural reading: the clause that names them is §17.1's, both rows sit in the edge-sequence table with `Loc::RootHistoryEdge`, and a validator that refuses them is refusing exactly what the clause states. For the chain reading: the word stale in §17.2 means superseded on a chain, and a structural refusal that counted as an answer would let a report satisfy a question about chain state, which §1.14 forbids (`plans/guides/guide_fourteen.md:414–430`). D2 proceeds on the structural reading with the chain reading carried as D8's residual, but which the guide intends is a question about §16.8's text rather than about this tree, so it is not settled here.

**OQ2. Whether the two new evidence boundaries are two members or one.** D7's retyping needs a boundary for each report, and §1.14 keeps root-history continuity and public successor recovery as separate evidence classes (`plans/guides/guide_fourteen.md:423–424`), which argues for two. Against two: `EvidenceBoundary`'s existing members name where a refusal happened rather than which report read it, and the report layer already has exactly one member covering a whole class of rows, `ReportSemanticProjectionRejection` (`packages/vectors/src/matrix.rs:245–246`). The bites proceed on two, because one member routing to two standings would decide the standing from the row's section and so state one rule in two places — the failure `from_native_refusal`'s doc names as the reason wrong-boundary rows once stood as answered — "one rule with two implementations is how wrong-boundary rows came to stand as answered before" (`packages/vectors/src/maturity_evidence.rs:1241–1249`). Whether §1.5's boundary list admits both is a question about the guide's own vocabulary.
