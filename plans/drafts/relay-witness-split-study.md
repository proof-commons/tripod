The source distinction for nonce is deliberate: `state_abi.rs:921–923` assigns its source to successor search; `packages/linker/src/state_carrier.rs:1013–1028` attributes its consumer to successor reconstruction; `state_program.rs:315` obtains its width from CopyThrough. The canonical layout is 21 domain bytes plus four schema bytes plus five eight-byte semantic fields plus the nine-byte maturity encoding plus four nonce bytes plus eight reserved zeros: 21 + 4 + 40 + 9 + 4 + 8 = 86. The domain is `tripod/state-metadata`, schema is big-endian 1 (`packages/realization/src/state_codec.rs:19–25,132–155`); the independent width and byte-order tests are `packages/realization/src/tests/state_codec_tests.rs:198–234`. Constant ranges are `[0,21)`, `[21,25)`, `[78,86)`, totaling 33. Potentially variable ranges are `[25,65)`, `[65,74)`, `[74,78)`, totaling 53. “Potentially variable” describes the general codec: an admitted announcement predecessor is Unannounced, so its maturity tag and payload are constrained, not nine independently free bytes (`state_codec.rs:146–149,206–213`; `state_announcement.rs:574–578`).

The metadata commitment script is three instructions: push the 86-byte metadata, push the empty item (`OP_0`), then `OP_VERIFY`. Its serialized bytes are `4c 56 || metadata || 00 69`, totaling 90; its tapleaf preimage is `c4 5a 4c 56 || metadata || 00 69`. The `0xc4` is the leaf-version byte in the preimage/control, not an instruction prepended to the script. `OP_0 OP_VERIFY` aborts independently of inherited stack contents (`packages/tapscript/src/state_constructor.rs:227–254`; `tests/state_constructor_tests.rs:1042–1046,1215–1227`). That non-executable leaf is distinct from the 1,286-byte announcement leaf.

Instruction trace, in execution order: the composed program first runs operator authorization, then structural recognition, then the five semantic components (`packages/tapscript/src/state_program.rs:245–298`). MetadataAuthentication starts with `ROT ROT CAT SWAP` to pack the static root and metadata beneath the predecessor prefix; it introspects input 0's script, verifies version 1, concatenates prefix and introspected coordinate, and takes a 33-byte key. It duplicates the packed value and `SUBSTR`s `(32,86)` to recover metadata for hashing. After tweak verification it recovers the retained root with `(0,32)` and metadata with `(32,86)` (`packages/tapscript/src/state_announcement.rs:421–446`). Those are all the authentication-side manipulations of the large item, including the initial 118-byte packing.

`hash_metadata` does not push a reconstructed 90-byte script as one item. It streams the exact equivalent preimage: a 64-byte double tag hash for `TapLeaf/elements`, concatenated with [c4,90,4c,86], initializes SHA-256, updates with all 86 metadata bytes, then finalizes with [00,69]. It initializes `TapBranch/elements`, updates with the metadata leaf hash, extracts the retained static root from the packed item, and finalizes in fixed metadata-left/static-right order. It then hashes `TapTweak/elements || internal key || branch root` and the caller checks the introspected compressed point with `TweakVerify` (`state_announcement.rs:391–417,437–440`). Thus all 86 bytes are authenticated, including domain, schema, old maturity payload, nonce and reserved zeros, even where no field is semantically sliced.

MaturityPredecessor duplicates metadata and checks the one byte at offset 65 against byte zero. LeadWindow duplicates metadata/request, slices cycle `[57,65)`, reverses the big-endian cycle one byte at a time with `SUBSTR` and `CAT`, biases unsigned comparison with XOR, adds each lead using checked 64-bit arithmetic, and checks both inclusive bounds (`state_announcement.rs:449–513,574–578`). CopyThrough takes `[0,65)`: this copies the domain/schema and all five unaffected fields together, not five separate field slices. It appends tag 1, requested big-endian cycle, the witnessed successor nonce, and eight reserved zeros, then takes 86 bytes (`state_announcement.rs:516–532`). The predecessor nonce is authenticated but not reused as the successor nonce. SuccessorReconstruction verifies output 0 asset and explicit amount, then reuses authentication with output introspection and without retaining the root (`state_announcement.rs:535–556`). FinalTruth drops the derived metadata and pushes true (`state_program.rs:228–239`).

The script uses strict `OP_SUBSTR`, `OP_CAT` and streaming SHA-256; it uses neither `OP_LEFT`, `OP_RIGHT`, `OP_SIZE` nor ordinary `OP_SHA256` in the archived announcement. The inspected reviewed registry has 55 opcode entries, independently listed at `packages/target-elements/src/tests/opcode_tests.rs:24–79` and checked against `OpcodeId::ALL` at lines 164–188. It includes CAT, SUBSTR and SIZE, the streaming trio, checked 64-bit arithmetic/comparisons/conversions, introspection and tweak verification. Ordinary SHA256, LEFT and RIGHT are supported by the host interpreter but absent from that reviewed 55-entry vocabulary (`elements: src/script/interpreter.cpp:1023–1147,1438–1462,1736–1797,2020–2037`; `script.h:143–148,195,225–227,255–268`). Using them in Tripod would require a reviewed-contract extension; none of the proposed transport adapters needs that extension.

Every shape retains the existing CAT/SUBSTR/streaming-hash machinery. A, B and D add CAT operations; C needs no additional opcode. None requires LEFT, RIGHT or ordinary SHA256. Other two-piece cuts are possible: both pieces fit policy when the cut lies from 6 through 80 inclusive; 65+21, 43+43 and 80+6 have the same four-byte join adapter. Three or more pieces add role/index work without a need imposed by 86 bytes. A 61-byte suffix with the 25-byte prefix synthesized is also possible: a five-instruction, 30-byte adapter gives approximately 1,316 script bytes. These are transport alternatives supported by CAT, not additional constructor generations (`state_codec.rs:132–155`; `state_announcement.rs:421–446`).

For B, the local stack proof is `root,head,tail,prefix → root,tail,prefix,head → root,prefix,head,tail → root,prefix,metadata → root,metadata,prefix`. It reaches the current authentication precondition exactly. All five semantic components after that boundary retain their current instructions and field offsets; only the predecessor authentication entry accepts a split. SuccessorReconstruction continues to receive a derived whole 86-byte item (`state_announcement.rs:259–325,421–446,535–555`).

Recommendation: B with the 78/8 cut, because it gives the smallest added executable adapter and the narrowest enforcement argument: concatenate the exact bytes previously authenticated, then run the existing checks. Its cost is one additional public ABI role and shifted later indices. D has the smallest item-map disturbance and is the strongest alternative if preserving seven roles is preferred; A saves more witness payload but embeds both constant regions and adds more script bytes. A/D rely explicitly on the canonical predecessor invariant when synthesizing omitted bytes; they are equivalent over admitted canonical states, not a demonstrated equivalence over arbitrary malformed authenticated encodings. C changes the committed language and is disproportionate to a six-byte policy excess. This recommendation is a proposed tradeoff, not a claim that B minimizes every file count.

The size estimates omit optional exact-piece-length guards. The existing leaf slices the needed 86-byte region and does not issue an `OP_SIZE == 86` guard (`state_announcement.rs:428–446`). B's minimal adapter therefore permits different partitions whose concatenation is identical; 78/8 is the deterministic builder schedule, not newly enforced by those four instructions. A ruling could instead add SIZE/equality guards, but that adds transport checks and changes the size/check census. The plan below chooses the minimal adapter, tests equivalent repartition explicitly, and keeps exact builder widths distinct from the script's accepted language.

For the same one-input/one-output framing and unchanged fixed-width keys, signatures, nonces and control depth, estimated total bytes/weight are A 1,701/2,091; B 1,699/2,089; C 1,676/2,066; D 1,698/2,088. These follow from today's 1,694 bytes, stripped 130, and `weight = total + 3×stripped`; B also adds one item-length byte (`packages/transaction/src/bytes.rs:114–118,947–960`). They are sizing estimates, not fresh target observations or a claim that the old transaction can be patched without rebuilding and signing.
